# ADR-0028: The patient portal: a server-side client of the api, with its own sign-in and a token keeper for each session

- **Status:** accepted (the nine points of the Decision validated one by one by the project owner on 2026-10-19; Phase 7, step 2; the ADR as a whole, with its updates of steps 3 to 6 and the words that no mock-up had that they list, approved by the owner on 2026-10-24)
- **Date:** 2026-10-19

## Context

`web` is the patient portal: pages rendered on the server for a person who signs in with SSO and sees only their own record. The owner decided on 2026-10-17 that it is a *server-side client of the api* (a "backend for frontend"): the browser holds one cookie and nothing else, the tokens never leave the server, and the portal asks the api for everything with the patient's own access token, so the api keeps deciding what a person may see (ADR-0012). Only a `patient` may use it. The realm already has the client `pulse-web`: confidential, PKCE `S256` required, redirect address `http://localhost:3300/oauth2/callback`, post-logout addresses `http://localhost:3300/*`, and the audience `pulse-api` in its access tokens.

Four things make it more than a redirect to Keycloak:

- **Access tokens last 5 minutes and a visit lasts longer.** The portal has to renew them, for each person, without two requests of the same person renewing at once, and without ever sending an expired token to the api. Keycloak's session behind them lasts 30 minutes idle and 10 hours at most (`ssoSessionIdleTimeout` 1800, `ssoSessionMaxLifespan` 36000).
- **The sign-in is where an identity enters our server from the browser.** A callback that is not the answer to a sign-in this browser started (login CSRF), a session that survives the sign-in with the same id (fixation) and a return address that leads off the site are the usual ways to get it wrong.
- **A session on the server is state that grows.** Whatever holds them must forget them, and an anonymous visitor must not be able to fill it.
- **The page has a strict CSP** (`script-src 'self'`, no inline script or style), which decides how htmx is configured and where a form may send its data.

The plan said to try `ring-oauth2` 0.3.0 first (a spike of at most an hour, in a scratch directory outside the repository) and to decide with what it showed. This is what it showed. Everything below was run against the real Keycloak with the new login theme, and the browser was headless Chrome 155.

**`ring-oauth2` 0.3.0** is one namespace of 217 lines. Used as its README says, with `wrap-params` and `wrap-session`:

- It works. `/oauth2/login` redirects to Keycloak with `state` and an S256 challenge; Ana signed in through the Pulse login page and came back; the session then held, under `:ring.middleware.oauth2/access-tokens`, the access token, its expiry as a `Date`, the **refresh token**, the **id token** and the rest of the answer. It sent the client's credentials with HTTP Basic when asked (`:basic-auth? true`).
- It does nothing with the refresh token: **there is no refresh**. Keycloak's refresh grant answers 200 with a new access token, a new refresh token and a new id token (`expires_in` 300, `refresh_expires_in` 1800), and accepts the old refresh token again (the realm does not revoke on use), so a renewal of our own is easy to write and cannot lock a person out by a lost race.
- **The session id is the same before and after the sign-in** (`ring-session` cookie compared at the launch and after the callback): nothing renews it. Ring does it when the response's session carries `:recreate` in its metadata (read in `ring.middleware.session`).
- **The `state` check passes when both sides are missing** (`(= nil nil)`). A callback with a `code` and no `state`, from a browser with no session at all, reached the token endpoint with `code_verifier=""`. Keycloak refused it because it requires PKCE for this client, so nothing was exposed; but the protection of the callback then depends on a setting of the server and not on the client.
- A code the provider refuses is an exception of clj-http, which nothing in the library catches: a 500 with no page. A provider error (`error=access_denied`, with the right `state`) is answered "No authorization code" with a 400 and the reason is lost. The exception's data holds neither the secret nor the request, which is to its credit.
- **No timeouts.** The token request is built inside the library with clj-http's defaults, which are none. The platform's own clients all have them (ADR-0021).
- No `nonce` and no way to add a parameter to the authorization request (`prompt`, `login_hint`); a relative `redirect-uri` is resolved against the request's `Host` header.
- It pulls in **clj-http 3.13 and 16 more jars** (Apache HttpClient 4.5, Cheshire as a second JSON library, potemkin, slingshot...) next to the `java.net.http` client that `pulse.platform.token` and `pulse.platform.http.client` already use. The backlog records clj-http as rejected (section H).
- Its launch writes a session for every request, and Ring's memory store has no expiry and no limit (read in `ring.middleware.session.memory`; the protocol's own docstring says a store should come with one): a loop of requests to the sign-in address fills the memory.

Making it safe would take a wrapper for each of those (renew the id, require a state, catch the exchange, read the provider's error, set timeouts through clj-http's middleware, verify the tokens, choose where to land) around about a hundred lines of flow we would still depend on. And what is left of the library after that is the launch redirect and the code exchange.

**Our own flow**, tried in the same spike in about 60 lines on the platform's pieces (`java.net.http`, `jsonista`, `pulse.platform.jwt`): the authorization request with `nonce` (the id token came back with it), the code exchange with Basic authentication, a code used twice refused (`invalid_grant`, and the tokens of the first exchange stopped working too: Keycloak takes back what a replayed code had given), a wrong `code_verifier` refused ("PKCE verification failed"). A **per-session keeper**, `pulse.platform.token/source` (ADR-0021) with a `:fetch` that makes the refresh grant and keeps the refresh token it gets back, started from the first token: twenty threads asking at once for a token that was near its end made **one** refresh grant; nineteen used the token they had, still valid, and one got the new one; later calls made none; a second renewal used the refresh token from the first; after the sign-out at Keycloak, a renewal answered `::unavailable` with `:reason :rejected`, `:status 400`, `:error "invalid_grant"` and the next call `:backing-off`.

**Sign-out** at Keycloak's end-session endpoint: with `id_token_hint` and a registered `post_logout_redirect_uri` it redirects straight back (302) and clears the SSO cookies, and the refresh token of that session then fails with `invalid_grant` ("Session not active"); without the hint, and with the SSO cookies, it shows the confirmation page of our theme ("Sign out?"); with an address that is not registered it shows an error (400) and redirects nowhere. An id token that had expired (335 seconds old; the platform's verifier called both tokens `:expired`) was accepted as the hint all the same, and the refresh token of that moment still worked (200) until the sign-out, so a person who comes back after the 5 minutes is renewed, and one who signs out late is signed out.

**Cookie and CSP in the browser.** The cookie from Ring's session middleware set with `:same-site :lax` arrived as `ring-session; HttpOnly; SameSite=Lax; Path=/`, a session cookie (it goes with the browser), and `document.cookie` did not show it. **A page with `form-action 'self'` could not sign out**: its form posts to the portal, the portal answers 303 to Keycloak, and Chrome applies `form-action` to that redirect too ("Sending form data ... violates the following Content Security Policy directive: form-action 'self'. The request has been blocked.", and no request reached Keycloak). With `form-action 'self' http://localhost:8080` it went through.

## Decision

**1. The sign-in is our own authorization-code flow, with PKCE (S256), `state` and `nonce`; `ring-oauth2` is not used.** It lives in `apps/web` (`pulse.web.oidc`: the authorization address, the PKCE pair, the code exchange and the end-session address, which are small functions of data) and the platform gains what it should have: the POST to the token endpoint that `pulse.platform.token` makes for the client-credentials grant becomes a function that the authorization-code and refresh grants use too (Basic authentication, timeouts, an `::unavailable` with a `:reason`, the answer and the secret never in an error). The addresses are built from configuration (`WEB_BASE_URL`, `http://localhost:3300`), never from the `Host` header. The dependency list of the owner loses `ring-oauth2` (and clj-http with it).

**2. Sessions are on the server; the browser has one opaque cookie.** `pulse.web.session` implements Ring's own `SessionStore` protocol over memory (so another store, Redis, can replace it: X-92), with what Ring's memory store lacks: an **idle** limit of 30 minutes and an **absolute** one of 10 hours (the two numbers of the realm; Keycloak stays the authority, and when it ends the SSO session the next renewal says so), and a **maximum** number of sessions. A sign-in that has begun and not ended is a *pending sign-in*, a different and smaller kind of entry (10 minutes, at most 1 000: when full, the oldest pending one goes, never a signed-in session), so an anonymous visitor cannot fill the store or push a person out. The callback finds the pending sign-in by the cookie, requires the `state` to be present and equal to the one it holds (compared in constant time), deletes it, and only then talks to Keycloak; a callback with no pending sign-in, an expired or a replayed one answers a page ("That sign-in has expired. Start again.") and **sends nothing to the token endpoint**. The signed-in session is a **new** entry with a new id, so nothing from before the sign-in survives it. The cookie: `HttpOnly`, `SameSite=Lax` (it must come with the top-level redirect back from Keycloak), `Path=/`, no `Max-Age`, and `Secure` when the public address is https (the production profile requires it; plain `http://localhost` is only for development).

**3. The tokens of a session are held by a keeper, and the portal calls the api with it.** The session holds a `pulse.platform.token/source` with a `:fetch` that makes the refresh grant, started from the grant of the code exchange (a small addition to `source`: an `:initial` grant), so the single flight, the early renewal (a minute before the end), "never an expired token" and the back-off of ADR-0021 are the ones already tested. `pulse.platform.http.client` takes the keeper as its `:token`, so a request is `(http/get-json (assoc api-client :token (:tokens session)) "/api/me")`, with the request id forwarded in `X-Request-Id`. The tokens are never in the cookie, never in a page, never in a log: the id token, which sign-out needs, is a `Secret`, and an event names the client and the reason and nothing else. When the keeper cannot renew because Keycloak refuses (`:rejected`) the session is ended and the person sees "Your session has ended" with a button to sign in; when it cannot renew because Keycloak is unreachable (`:connect`, `:timeout`, `:server`) the person sees "Sign-in is not available right now" and the session stays, because the next try may work. At the sign-in the portal verifies both tokens with `pulse.platform.jwt` (access: issuer, audience `pulse-api`, `typ` Bearer; id: audience `pulse-web`, `typ` ID, and the `nonce` it sent), and reads the person's name for the header from the id token.

**4. Only a `patient` gets in.** The decision is on the verified roles of the access token. Anyone else, an administrator or a doctor, gets a page "This portal is for patients" (403) with a link that signs out (without an id token in the address: Keycloak asks for confirmation), **no session is created**, and the refusal is audited with the shape of the other audit events (`:pulse.audit/access`, the action `:portal/sign-in`, `:denied`). This is for the person's sake, not for security: the api still decides what any token may see.

**5. Signing out is a POST with a CSRF token.** It deletes the session first, then answers 303 to Keycloak's end-session endpoint with `id_token_hint` (the last id token the keeper was given; every renewal gives a new one) and `post_logout_redirect_uri` (`WEB_BASE_URL` + `/signed-out`, a public page that says so and offers to sign in). The portal's session is gone before the browser is sent to Keycloak, so a Keycloak that does not answer leaves the person signed out of the portal.

**6. CSRF: `ring-anti-forgery` 1.4.0, plus `SameSite=Lax` and a check of `Origin`.** The synchronizer token lives in the session; forms carry it in a hidden field and htmx sends it in the `X-CSRF-Token` header, set once with `hx-headers` on `<body>`. Every unsafe method (POST, PATCH, DELETE) is also refused when it has an `Origin` header that is not the portal's. The pages that change something (record a reading, request an appointment, cancel, sign out) are POSTs; GETs change nothing.

**7. CSP and headers.** `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; object-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'self' <the origin of Keycloak>` (the origin that Keycloak has for the browser, from configuration; the finding above), the rest of the headers from `pulse.platform.http.headers` (`nosniff`, a `Referrer-Policy`, HSTS when https), and `Cache-Control: no-store` on every page that holds personal data. htmx, the stylesheet and the font are files of the portal (`resources/public`, htmx copied from the npm package with its licence in `NOTICE`, the stylesheet compiled and committed like the login theme's). htmx is configured with `<meta name="htmx-config" content='{"allowEval":false,"includeIndicatorStyles":false}'>`: it would otherwise inject a `<style>` element, which `style-src 'self'` blocks, and the style of the indicator is in our stylesheet. The policy is checked in headless Chrome with a control that must be blocked (step 8), as the api's was.

**8. The routes are data, with deny by default.** Each route says `:authz :public` or `:authz :patient` (the key of the api's and the scheduler's routes, so the platform's traversal of the router finds the routes that say neither), and the start-up fails when one does (as the api's `check-routes!`). Public: `/healthz`, `/readyz`, `/sign-in`, `/oauth2/callback`, `/signed-out`, the assets. A request to a `:patient` route with no session is a 303 to `/sign-in`; if it is an htmx request (`HX-Request: true`) the answer is a 401 with an `HX-Redirect` header, so that htmx navigates the whole page and never swaps a sign-in into a fragment. The address to return to (`return-to`) is kept in the pending sign-in, on the server, and is accepted only as a path of the portal (it starts with one `/`, not `//`, no backslash, no scheme); otherwise it is `/`. A provider error at the callback (`error=access_denied`) is a page with our words, never the provider's `error_description`, which goes to the log. The pages for a failure of the api (502, 504 as the api's problem says) and the 404 and 500 pages are the portal's own, in the words of the mock-ups.

**9. How it is tested.** The fake identity provider of the platform (`pulse.platform.test.idp`, which has `/token` and the JWKS) learns `/authorize` (it records the request and redirects with a one-use code and the state), the code exchange (it checks the PKCE verifier, the redirect address and the client, and signs an access token and an id token with the `nonce`), the refresh grant (the refresh token it gives can be the same or a new one, to test both) and the end-session endpoint (it checks the hint and the registered address). Tests drive the whole flow over HTTP with a cookie jar, and check among other things: no request reaches the token endpoint without a state; the session id changes at the sign-in; a replayed callback fails; twenty requests at once on a token near its end make one refresh; an expired session, a refused refresh and an unreachable Keycloak give three different pages; a doctor's token gets no session; the `Origin` and CSRF checks; a property over `return-to` (nothing off the site is ever accepted). With `bb test:it`, the same against the real Keycloak (Ana signs in through the theme, the session, a refresh, sign-out, and the refresh refused afterwards); in step 8, a headless browser walks the portal.

**Configuration and commands.** `WEB_PORT` (3300, read like `SCHEDULER_PORT`), `WEB_BASE_URL`, `WEB_CLIENT_SECRET` (`#secret`, already in `.env`), the addresses of Keycloak (the browser's and the back channel's, as the api has them), `API_BASE_URL`. `bb web` runs the portal alone; `bb dev` starts it with the api and the scheduler in one JVM. No change of the realm is expected: `pulse-web` already has what this needs.

**Dependencies.** New: `ring/ring-anti-forgery` 1.4.0, `ring/ring-mock` (tests only), htmx 2.x as an npm development dependency of `design/` that is copied. Not used any more: `ring-oauth2`.

## Alternatives considered

- **`ring-oauth2` with wrappers** (what the plan expected): about a hundred lines of wrapping around the part of it we would keep, a second HTTP client and a second JSON library on the classpath, and each wrapper a place where a future change of the library could undo a protection without a test noticing; against the cost of owning about sixty lines of a flow that two RFCs describe and that the fake provider tests anyway. The honest cost of ours is that it is security code we maintain; the spike's experiments are the first of its tests.
- **Tokens in an encrypted cookie** (no state on the server): the three tokens are about 3.3 KB before encryption and encoding, against a limit of about 4 KB for a cookie; renewal could not be done once for a person (two tabs renew at once and the cookie of one wins); and a session cannot be ended from the server.
- **The portal calling FHIR directly:** it would have to repeat the authorization, the audit and the contract of the api (ADR-0004, ADR-0012).
- **A proxy that signs people in in front of the portal** (oauth2-proxy and the like): not Clojure, and the portfolio is about the Clojure.
- **A session in Redis or a database now:** the store is Ring's protocol so that it can be one day (X-92); a second service in the stack is not worth it for a demo.

## Consequences

- A restart of the portal ends every session (they are in memory): the next click shows "Your session has ended". There is one portal process; the keepers are objects in it. Both go in X-92.
- The access token the api accepts stays valid for up to 5 minutes after a sign-out (verification is stateless, ADR-0009). The portal throws its copy away at once; nobody else has it.
- Keycloak is asked about once every four minutes for each person who is active, and not at all for one who is idle; an idle person's renewal on the next click works if they come back within 30 minutes.
- If Keycloak signs the person out somewhere else (another application, the account console) the portal learns it at the next renewal, up to 5 minutes later. Telling it at once is OpenID Connect's back-channel logout (X-91).
- The platform changes a little (`token/source` with `:initial`, the shared POST to the token endpoint), with tests there, and `apps/web` begins with the part of the flow that is most worth testing.
- The CSP names Keycloak's origin in `form-action`, which is the price of signing out with a form; the alternative, a link, would need no CSRF token and let any page sign a person out.

## Update, 2026-10-19 (step 3, the skeleton of `apps/web`)

What building the skeleton settled, without changing a decision above:

- **The key of a route is `:authz`**, not `:access` (point 8): the same word as in the api and the scheduler, and `pulse.platform.http.router/endpoints-without` finds the hole without a second traversal. `:patient` is enforced already: a route with it gives its page to whoever the session of the request says is a person (`(:person (:session request))`), and sends everybody else to the sign-in; the sign-in and the session are step 4.
- **The Referrer-Policy is `same-origin`, not `no-referrer`.** A browser that has been told `no-referrer` sends `Origin: null` with a form it posts to its own server, which would make the check of the `Origin` of a request that changes something (point 6) unable to tell a form of the portal from one a sandboxed page made. With `same-origin` the form carries the portal's origin and the identity provider is told nothing of where the person was. It is a test of `pulse.web.security`, and a check of step 8 (a plain form in headless Chrome).
- **htmx is configured more strictly than point 7 says:** besides `allowEval` and `includeIndicatorStyles` (false), `allowScriptTags` is false (no `<script>` in an answer is run), `selfRequestsOnly` is true, and `historyCacheSize` is 0: htmx would otherwise keep a copy of the pages a person visited in the storage of the browser, where the readings of a patient would stay after they signed out. The rules for the indicator are in the stylesheet of the portal (`design/css/web.css`).
- **The headers add `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Resource-Policy: same-origin`** (the portal opens no window and serves no one else), and HSTS and the `Secure` flag of the cookie wait for the sign-in, since they depend on the address the portal is served at (`WEB_BASE_URL`).
- **The platform grew three small things for it,** each with tests where it lives: `pulse.platform.http.client` sends no `Authorization` when it has no keeper (the portal's client of the api has none of its own: each call is given the keeper of a session with `(assoc client :token keeper)`; readiness asks the api's public `/readyz` with none), and never sends one that a caller put in the headers; `wrap-exceptions` takes `:unexpected`, the response for a failure nobody expected, so that a service whose answers are pages and not problems gives its page and still logs the cause; and `origin-of` moved from the api's `security` to `pulse.platform.http.headers`, since both policies name the origin of the identity provider.
- **The pages are written in `apps/web` and the mock-ups use them** (`pulse.web.pages`, pure and free of Ring, so Babashka loads it for `bb design:build`): the four cards of the mock-up `errors` are `pulse.web.pages/error-card`, and the portal's own pages for a path that is nothing (404, and 405 with its `Allow`) and for a failure (500) are the same card in a frame, with its title as the `h1`. `empty-state` of `libs/ui` gained `:heading` for that.
- **The static files** (`apps/web/resources/public`: the stylesheet compiled from `libs/ui` and the portal, the font with its license, the icon and htmx 2.0.11) are made by `bb design:web` and committed, as the login theme's are; a test checks that they are what the generator makes, that every class a page uses has a rule in the stylesheet and that htmx is the version `design/package.json` pins, which is exact.
- **Checked in headless Chrome 155** against the portal running: the 404 and the 500 pages load all they need and nothing else with no violation of the policy, at 390 and 1280 px, light and dark; and with a control: an inline script, an inline style element, a style attribute, `eval`, a request to another server and a form that goes to another server are all blocked.

## Update, 2026-10-21 (step 4, the sign-in, the session, the sign-out and the renewal)

What building it settled, without changing a decision above:

- **The platform gained what point 1 said it should.** `pulse.platform.token/endpoint` is the POST to the token endpoint of one client, as a function of a form, with its HTTP client made once: the client-credentials grant of the services (`http-fetch`) and the authorization-code and refresh grants of the portal all use it. It returns the grant with the refresh token and the id token as `Secret`s, and a 200 that is not a bearer token with a lifetime is a `:bad-response` there. `source` takes `:initial`, a grant in hand with the moment the request was sent (`:asked-at`), so the life of the first token is counted from when it was asked for, as a renewal's is, and is a record that prints as `#token-source[client]`: a keeper in the data of an exception or of a log event would otherwise print a bearer token.
- **The pending sign-in is taken atomically.** Point 2 said the callback deletes the pending sign-in before it talks to Keycloak. The store does it with `consume!`, a take that two requests cannot both win, so two identical callbacks cannot both pass the check and exchange the same code (the second exchange would make Keycloak take back the tokens of the first). The state is compared first, with what the request's session holds, and a callback whose state is not the right one leaves the pending sign-in where it is: a forged callback must not end the real one. A request that lost the race for it does not touch the cookie, which is the winner's by then.
- **The store keeps its limits whatever is written.** A write that would turn a pending sign-in into a session, or the other way, is a new entry that makes room as any other does (a test against a model of the store found that a rewrite let the sessions pass their limit). A key the browser chose is never a key of the store: a write for a key that is not there gives a new one. The store prints how many entries it holds and never what.
- **The tokens.** The scope asked for is `openid profile`; both tokens are verified by two verifiers made from the platform's component (`:pulse.web/access-verifier`, audience `pulse-api`, `typ` Bearer, and `:pulse.web/id-verifier`, audience `pulse-web`, `typ` ID), the `nonce` and the subject are compared by the portal, the name is the id token's (then the access token's, then the user name), and the session keeps the person (`:id :username :name`), the keeper and the CSRF token, and nothing else: not the roles, not a token.
- **What a person sees when a session is gone.** A browser that comes with the cookie of a session that is not there (it ended, or the portal was restarted) gets "Your session has ended" (401) and is told to drop the cookie; one with no cookie is sent to sign in without a word; htmx gets a 401 with `HX-Redirect` in both cases. When the portal ends a session (a refused renewal, a sign-out) the cookie is told to go. A renewal the provider refuses while the access token is still good is not shown to the person (the keeper gives the token it has, as ADR-0021 says): they work until it expires, at most the minute that the margin gives, and then the session is over.
- **Five more words that no mock-up had**, shown in the review page of the errors for the owner to say whether they are right: "That sign-in has expired" (400, a callback that is not the answer to a sign-in this browser began), "We could not sign you in" (400, the provider said no or a token was wrong), "Sign-in is not available right now" (503), "This portal is for patients" (403) and "We could not do that" (403, a request refused by the check of the origin or of the token). The page after signing out ("You have signed out") and the page of a person who is in, which says who they are and has the sign-out form until the home of step 5 replaces it, are the portal's own.
- **CSRF as built.** The token is 32 random bytes made at the sign-in and kept in the session; `ring-anti-forgery` checks it with a strategy that reads it (its own would make a session for a visitor that only asked for a page and write the whole session back). The check is for the routes that say `:authz :patient`, inside the check of who is signed in, so that a person whose session ended is sent to sign in and not told that a token they never had was wrong; the check of the `Origin` is for every request that changes something, before anything else, and refuses `null` too. A form carries the token in a hidden field and htmx in `X-CSRF-Token`, set once with `hx-headers` on the body (`layout/document` has `:body-attrs` for it). `ring-mock` was not needed (the handler is called with requests the tests build) and is not a dependency.
- **Served over https** (`WEB_BASE_URL` starting with `https://`): the cookie is `Secure` and every answer has `Strict-Transport-Security: max-age=63072000; includeSubDomains`. The address must be an origin (no path), since the redirect addresses are made from it and the `Origin` of a request is compared with it; it is `localhost` and not `127.0.0.1` because the realm registers `localhost`, and the cookie is of a host.
- **The fake provider** `pulse.platform.test.oidc`, on the fake of `pulse.platform.test.idp`, signs people in (`/authorize`), exchanges the code with the checks Keycloak makes (PKCE `S256`, the redirect address, one use, a replay ends the session), renews, and signs out (`/logout`, with the hint or asking first); it has tests of its own (`oidc-fake-test`), because a portal tested against a fake that is easier than Keycloak proves nothing. The same flow runs against the real Keycloak in `pulse.web-stack-test` (`bb test:it`).
- **Checked in headless Chrome 155** against `bb dev lite` and the real Keycloak (a scratch script over the DevTools protocol, not in the repository): 22 checks. The home page sends a visitor to the themed login page, and the authorization request has PKCE, `state` and `nonce`; the cookie the browser holds is `pulse-session`, `HttpOnly`, `SameSite=Lax`, a session cookie, and a script cannot read it; a plain form POST carries `Origin: http://localhost:3300` (and `Referer` of the portal), which is what `Referrer-Policy: same-origin` was chosen for; the sign-out form, answered by a redirect to Keycloak, is not stopped by `form-action 'self' http://localhost:8080`, and the browser comes back to the page that says so; no page of the journey violates the policy, with a control that must be blocked (an inline script, an inline style, a style attribute, `eval`, a request to another server); a doctor is told the portal is for patients and gets no cookie; after signing out the home page asks for the password again.

## Update, 2026-10-22 (step 5, the home)

What building it settled, without changing a decision above:

- **A request is the days that suit the patient, on the clinic's clock** (`pulse.web.visits/window`). The form asks for a first day and a last day; the window begins when the first day does and ends when the last one does (the start of the next day), so that asking from the 20th until the 20th is asking for that whole day, which a window that ended where the last day began could not.
