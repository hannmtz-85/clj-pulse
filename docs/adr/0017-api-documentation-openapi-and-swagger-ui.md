# ADR-0017: API documentation: OpenAPI generated from the route data, Swagger UI, and PKCE login

- **Status:** accepted
- **Date:** 2026-10-14

## Context

The plan asks for OpenAPI and Swagger UI at `/docs`, with a login so that each role can try the endpoints it may call (Annex B: `GET /docs`, public). The route table already says, in one place, the path, the method, who may call it (`:authz`) and the shape of what it takes and returns (malli), so the documentation can be generated from it instead of being written next to it. Open questions: which OpenAPI version and which generator; how Swagger UI is served and logs in (the realm has a public client `pulse-docs` with PKCE, redirect `http://localhost:4000/docs/*`); how the access rules, which are not part of a schema, get into the documentation; and what this public page may do and load, since it is the one part of the api that serves HTML.

## Decision

- **Generated, never written.** `reitit-openapi` turns the route data into the document, served at `GET /openapi.json` (public, and not in its own listing). Every operation has a summary, a description, tags, its parameters and request body (from the malli schemas that already coerce them) and its responses. The document is **OpenAPI 3.1.0**: the library's default is 3.2.0, which adds nothing the api uses, while 3.1 is what Swagger UI draws (it says so on the page) and what the validators and code generators in use today are sure to read. (3.1 is JSON Schema 2020-12, so a nullable value is `oneOf` a type and `null`, as malli writes it.)
- **The access rules come from `:authz`, the problems from `:problems`.** `pulse.api.docs/document` completes what Reitit generated, once, when the document is first asked for (the routes do not change while the api runs), reading the routes of the finished router, where what a route inherits is already applied. For each operation that is not public it adds the `oauth2` security requirement; the roles that may call it with the scope each has, read from `authz/rules` (written in the description, and as `x-pulse-access`); and the errors that every protected operation shares, as references to `components.responses` (problem details): 401 and 403, 404 when `:authz` names a `:resource`, 400 when the operation has parameters or a body, and `5XX` for what the api could not do (the FHIR server failing or slow, the keys of the identity provider missing). An endpoint says what only it knows in its route data, `:problems {409 "when" 422 "when"}`, which becomes a response with that text. The limits that the text quotes (30 days, 5 minutes) are read from the code that enforces them. Tests cross-check each operation's `x-pulse-access` and statuses against a table written apart from the code, so the documentation cannot say what the code does not.
- **Descriptions are data.** The text that explains an endpoint, a parameter or a field is in the route table and in the malli schemas (`:description` on an entry), next to what it describes, and a test requires one for every operation, parameter, response and field of a request body. Where malli's translation says too little (a `:fn` becomes an empty schema; a text with a net of 1000 characters is refused at 200 by the lifecycle), the schema carries what the document should say in `:json-schema`.
- **Swagger UI from a jar** (`reitit-swagger-ui` and `ring-swagger-ui`), under `/docs`, by a handler that comes before the router's answer for a path that matches no route: it answers GET and HEAD, and only for `/docs` and what lies below it by whole path segments (Reitit's own resource handler would take `/docsindex.html` for the page and answer any method). The version that `reitit-swagger-ui` pulls (5.32.11) does not contain `oauth2-redirect.js`, which the login needs, so the api depends on `ring-swagger-ui` 5.33.0 directly; a test fetches the page and the script, so the omission cannot come back. `/docs/config.json`, the library's, says where the document is and that no online validator is called: the page calls nobody but this server and Keycloak. Ring's resource handler refuses paths that climb out of the directory (`..`, encoded or not); tests pin it, since a classpath does hold the api's configuration.
- **Login: Authorization Code with PKCE (S256), public client `pulse-docs`.** The security scheme in the document points at Keycloak's authorization and token endpoints, built from the configured issuer, which is the address a browser uses. Swagger UI takes `clientId` and PKCE only through `ui.initOAuth`, not through its JSON configuration, so the api ships its own `swagger-initializer.js` (a resource of the api) and serves it by name at `/docs/swagger-initializer.js`: it points at `/openapi.json`, enables PKCE, asks for the `openid` scope and names the client. It is served by name, and not left to shadow the jar's, because which of two resources with one name a classpath finds is not something to rely on. Tokens are not persisted by the page. The audience mapper of the realm gives these tokens `aud: pulse-api`, so what Swagger UI obtains is what the api verifies; a test reads the committed realm and checks that the client the page names is public, uses PKCE, accepts the redirect the page returns to, allows the origin of the page and carries that mapper. Swagger UI shows a `client_secret` field all the same: the description of the scheme says to leave it empty.
- **A public page that can do little.** `/docs/*` and `/openapi.json` hold no clinical data and need no token. The page runs under its own Content-Security-Policy (ADR-0018): scripts and styles from this server, connections to this server and Keycloak, no framing. `Cross-Origin-Opener-Policy` is not set, because the login opens Keycloak in a popup that talks back to the page through `window.opener`, and that policy would cut the link.

## Alternatives considered

- **A hand-written `openapi.yaml`:** readable, but it is a second place where the api is described, and it drifts.
- **OpenAPI 3.2.0, the library's default:** the newest, with nothing in it that is used here.
- **Swagger UI from a CDN:** nothing to ship, but the page would load code from a third party, which a Content-Security-Policy would forbid and a clinical api should not do.
- **Writing the access rules by hand in each description:** they would be right on the day and wrong later. `authz/rules` is the single source.
- **Deriving the documentation while the router is built**, with the router's `:coerce` option or a walk over the raw route table: `reitit.ring/router` already uses `:coerce` for its own work (and its function is private, so it cannot be composed), and a walk would re-implement Reitit's syntax for routes. The resolved routes of the finished router have everything, inheritance included.
- **Letting our `swagger-initializer.js` shadow the jar's on the classpath:** shorter, and it works on a development classpath, but an uberjar holds both and the order is not ours to say.
- **Redoc or Scalar:** better reading, but they cannot try a request with a login, which is the acceptance criterion.
- **A formal check of the document against the OpenAPI 3.1 schema in the tests** (swagger-parser, or a JSON Schema validator and the schema vendored): a heavy dependency for a guarantee that the structural tests below mostly give; in the backlog.

## Consequences

- Adding an endpoint documents it: route data, schemas, `:authz`, and a summary, a description, tags, descriptions of its parameters and fields and of its responses, as before, plus `:problems` for a 409 or a 422; nothing else. Forgetting any of them fails a test, as does forgetting to add the operation to the table of the tests.
- `/docs/` is outside `check-routes!`, as a handler and not a route. It exposes nothing the document does not.
- Checked in a real browser (headless Chrome 155, Swagger UI 5.33.0, the real Keycloak and HAPI): the page draws the 13 operations and says OAS 3.1; Authorize opens the popup at Keycloak with `client_id=pulse-docs`, `scope=openid`, `code_challenge_method=S256` and the redirect `http://localhost:4000/docs/oauth2-redirect.html`; after the login the page exchanges the code for a token, which the browser lets it read because the client allows the origin of the page, and says Authorized; Try it out then sends `Authorization: Bearer …`. As a patient, `GET /api/patients` and `GET /api/alerts` are 403 and `GET /api/appointments` returns the patient's own; as Dr. Rivera, `GET /api/patients` returns the four of the panel; as the administrator, all six. Nothing was blocked by the policy, and a control (an inline script, a `fetch` to another origin) was.
- The malli maps are closed, so the schemas of requests and responses say `additionalProperties: false`, while the api in fact strips what a request carries that the schema does not name. The document is stricter than the api in that, never looser.
- `GET /api/admin/jobs` will appear in the document by itself when it exists (Phase 5).
