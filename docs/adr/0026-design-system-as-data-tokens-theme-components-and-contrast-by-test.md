# ADR-0026: The design system as data: tokens in EDN, a theme generated from them, shared hiccup components and contrast checked by a test

- **Status:** accepted (the approach was validated point by point by the project owner on 2026-10-16; Phase 6). At the first review, the same day, the owner approved the style tile and chose **teal**: see the update at the end of the decision.
- **Date:** 2026-10-16

## Context

Phase 6 gives the three interfaces one look: `web` (the patient portal, rendered on the server with Hiccup and htmx), `spa` (the clinical workspace, Reagent) and the login page of Keycloak (FreeMarker). The plan names the pieces (Tailwind 4 and daisyUI 5, a light and a dark theme, AA contrast, a sidebar and header layout, components, a chart style, navigable mock-ups and a final login theme) and one rule: the owner approves the mock-ups before any interface is written. Four things have to be decided:

- **Where the look is defined**, so that three technologies share it and a colour is changed in one place.
- **How the AA claim is made true, and stays true**, when every palette and both themes have to meet it.
- **How a component is written once** for a server that renders strings and a browser that renders React.
- **How the owner reviews it** without the work being done again after each remark.

## Decision

**The tokens are data.** `design/tokens.edn` holds the palettes (three candidates at first, teal, blue and indigo: the owner chooses one at the first review and the others are deleted), each with a light and a dark scheme; the neutrals; the tones of a reading's band (normal, and three degrees away from it, the four that `pulse.fhir.ranges/severity` has); the colours of a chart; the typography, radii and shadows; and the list of **pairs of colours that must meet a contrast**, with the ratio each needs: 4.5 for text and 3 for what a person has to see to use a control or to read a graphic (WCAG 2.2 AA).

**A theme is generated from them.** `tools/design.clj`, which is the same under Babashka and on the JVM, writes `design/theme.css`: the daisyUI themes (`@plugin "daisyui/theme"`), the custom properties `--pulse-*` for what daisyUI has no variable for (the tones of the bands, the border of a control, the colours of a chart), and the `@font-face` of the font. It is committed and checked by `bb design:check`, part of `bb check`, as the realm JSON is.

**Contrast is a test.** The ratio is the WCAG formula, a pure function. The test fails when any pair of any palette in either scheme is below its minimum, and the style tile prints the measured ratio beside each swatch, so that the owner sees the numbers and nobody has to take them on trust.

**Tailwind 4 and daisyUI 5 are built from npm.** `design/package.json` pins Tailwind CSS and its CLI, daisyUI, the Inter font (variable, OFL) and the Lucide icons (ISC), all for development; `node_modules` is ignored by git and the lock file is committed. Tailwind reads the Clojure sources for class names, so **a class is written whole, as a string literal**: `"btn btn-primary"`, never `(str "btn-" kind)`, which it cannot see. The font is in the repository as files and the icons as Clojure data (`libs/ui`, generated by `bb design:icons`); no page asks a CDN for anything.

**Components are shared hiccup.** `libs/ui` (`.cljc`) has presentational functions, `(button {:variant :primary} "Save")`, that return hiccup data: no state and no handlers, and the attributes they are given go through, so the `hx-*` attributes of htmx and the `:on-click` of Reagent both work. They are rendered to strings by Hiccup 2 in `web` and by React in `spa`. A chart is a function from data to SVG (`pulse.ui.chart`), accessible by construction: a role, a title, a description and a table of the same numbers. Charts are drawn for a width: the portal draws a compact one and a wide one and shows the one that fits.

**The mock-ups are generated.** `bb design:build` renders the pages from the components, with real data from the synthetic cohort, to static HTML in `design/dist/` (ignored by git), with an index to move between them, and `bb design:shots` makes screenshots with headless Chrome so that they can be looked at without opening each. There are two points of review: first the style tile (the palettes, the type, every component and a chart, in light and dark), then the pages.

**The Keycloak login** is a theme of FreeMarker templates over the `keycloak` theme: the frame and the pages that exist in our flows (sign-in, error, information, logout confirmation and expired session), with the same compiled CSS. That CSS is committed in the theme, because the stack must start without Node.

**Accessibility** is WCAG 2.2 AA: the contrast by the test above; a visible focus ring that comes from a token; targets of at least 44 px in the portal; no meaning conveyed by colour alone (a band has an icon and a word, a series of a chart a dash and a marker); reduced motion respected. What a program can see in hiccup is checked by a test of its own, `pulse.ui.test.a11y`, which every component and every page of the mock-ups must pass (labels of controls, names of buttons and links, svg hidden or named, ids that exist and are unique, captions and scopes of tables, headings that do not skip a level, and for a page the language, the title, the viewport, one h1 and a main). Focus order, reflow and the size of targets are checked by hand until the extra X-32.

**Update, 2026-10-16: the first review.** The owner approved the style tile (the look, the components, the way a reading away from normal is shown) and chose teal. Blue and indigo were deleted from `design/tokens.edn` in a commit of their own, `:palette :selected` is `:teal`, and the themes are called `pulse` and `pulse-dark`; the generator still writes a theme for each of several palettes when none is selected, and the tests of that use the tokens of the review, made in the test. The same review decided that a patient can cancel their own appointment, which the plan and Annex A did not allow (the portal said "request/cancel" and Annex A gave the patient only the request): the mock-ups have the button, and the api gets the action in Phase 7, with its own ADR.

## Alternatives considered

- **Tokens written in CSS (`@theme`)**: how Tailwind 4 is meant to be used and the shorter way; the contrast would be checked by eye, and Chart.js, the SVG of the portal and the login would each read the colours in a different way.
- **A token tool such as Style Dictionary**: another Node program for what is a hundred lines of Clojure that the repository already knows how to test.
- **Tailwind without daisyUI**: every component by hand, in three technologies.
- **The play CDN of Tailwind and a CDN stylesheet of daisyUI** for the mock-ups: no build, but nothing a page needs should depend on the network, and the CSS would not be the one that ships.
- **Mock-ups written by hand in HTML**: quicker today and written again in Phase 7. A component in `libs/ui` is written once.
- **The components in `web` and copied to `spa`**, or the reverse: two that drift apart.
- **The design in a tool such as Figma**: outside the repository, and not data.

## Consequences

- There is a Node toolchain in the repository, for development only (Phase 8 needs it anyway, for shadow-cljs).
- Two build steps: Clojure writes `theme.css`, and Tailwind writes `pulse.css` from it and from the sources. Only the first is checked by `bb check`; the second needs Node.
- A class cannot be put together from parts. A component that needs one of several writes them all out: `{:primary "btn-primary" :ghost "btn-ghost"}`.
- The palettes that were not chosen were deleted, and the choice is a commit of its own (teal, 2026-10-16).
- The build of the mock-ups fails when a page uses a class that the compiled stylesheet has no rule for: a misspelling, or a class that was put together from parts, which Tailwind cannot see.
- In both schemes the page is the darker of the two surfaces and a card the lighter (in the dark scheme `base-100` is slate 800 and `base-200` slate 900), so that a card stands out from the page in light and in dark; the contrast test covers both.
- The compiled CSS of the login theme is a build artefact in git, like the realm JSON.
- `libs/ui` is what both `web` and `spa` depend on besides `libs/fhir`, and it depends on nothing but Clojure.
