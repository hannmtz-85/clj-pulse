# ADR-0030: Packaging the apps: compiled uberjars, two Dockerfiles, nginx for the workspace and a compose profile

- **Status:** accepted (the five choices of this ADR, with the defaults proposed, were validated by the project owner on 2026-11-04; Phase 9, step 1)
- **Date:** 2026-11-04

## Context

Until Phase 8 the four applications run on the developer's machine: `bb dev` starts the api, the scheduler and the portal in one JVM, `bb spa:serve` serves the workspace's release, and `compose.yaml` holds only the infrastructure (PostgreSQL, Keycloak, HAPI). There is no Dockerfile. CI (`ci.yml`) runs `fmt:check`, `lint` and `test`, which is less than `bb check` says it runs (`realm:check`, `design:check` and `spa:test` are missing: the owner asked on 2026-11-03 for that to be closed in this phase), and no integration test or journey runs in it.

Phase 9 asks for an image for each app, `docker compose --profile apps up` starting everything, the integration tests against the real HAPI and Keycloak, and an optional CI job. Its acceptance is a clean clone that runs `bb doctor && bb up && bb seed && docker compose --profile apps up`.

What shapes the decision:

- **Memory.** Docker Desktop is capped at 6 GB, the machine has little free RAM, and the infrastructure already takes about 2.5 GB (limits of 256 MB, 1 GB and 1.2 GB). Three more JVMs and a web server must fit in what is left.
- **Addresses.** Inside the compose network the apps reach Keycloak as `keycloak:8080`, HAPI as `hapi:8080` and each other by service name, while a browser reaches Keycloak at `localhost:8080` and the realm registers `localhost` addresses. The configuration already separates what a browser sees from what a service uses (ADR-0003, ADR-0009): `KEYCLOAK_ISSUER` (the `iss` of the tokens), `KEYCLOAK_AUTHORIZATION_URI` and `KEYCLOAK_END_SESSION_URI` are the browser's; `KEYCLOAK_JWKS_URI` and `KEYCLOAK_TOKEN_URI` are the service's. Keycloak has `KC_HOSTNAME=http://localhost:8080` and `KC_HOSTNAME_BACKCHANNEL_DYNAMIC=true` since Phase 2, and nothing has yet used the back channel from another container.
- **The policy of the workspace.** ADR-0029 (point 9) has the release served by our own Ring server so that its policy is tested now, "and nginx of Phase 9 copies it from the same data".
- **Nothing leaves the machine.** No image is pushed anywhere, everything binds to 127.0.0.1, and secrets come from `.env` and are never in an image.

**Evidence** (a spike on the owner's machine on 2026-11-04, with no Docker; the scratch files are not in the repository). `tools.build` makes a working uberjar of an app from its own `deps.edn`, with the libraries of the monorepo as `:local/root` (79 libraries; the sources and resources of the local ones are inside, and the manifest says `Multi-Release: true`): 18 MB for the api, 15.6 MB for the scheduler and for the portal. **Not compiled ahead of time it is slow to start**: the time until `/healthz` answers was 43 s for the api, 38 s for the scheduler and 33 s for the portal, because Clojure reads and compiles every namespace of every library from source at each start. **Compiled ahead of time from the main namespace** (24 to 26 MB, and the build of the api takes 2 min 40 s) the api starts in 8 to 10 s, the scheduler in 9 s and the portal in 6 s; the working set after thirty requests was 247 MB for the api with a heap of 256 MB, and 176 MB for the scheduler and 171 MB for the portal with 192 MB (the jobs of the scheduler were off). The C1 compiler alone (`-XX:TieredStopAtLevel=1`) saved another 1.7 s on the api. These are numbers of a Windows JVM; the ones in Linux containers will be measured.

## Decision

1. **An uberjar for each JVM app, compiled ahead of time.** `tools/build.clj` (alias `:build`, `io.github.clojure/tools.build` 0.10.14; `bb build [app ...]`) makes `target/<app>.jar` from `apps/<app>/deps.edn` and compiles `pulse.<app>.main` with everything it loads. The jar runs as `java -jar <app>.jar -m pulse.<app>.main`: the `Main-Class` is `clojure.main` and no application code changes for it. The configuration stays what it is: `config.edn` inside the jar, the values from the environment, the profile from `API_PROFILE`, `SCHEDULER_PROFILE` or `WEB_PROFILE` (`dev` in the containers: HAPI is a container, not a fake).
2. **Two Dockerfiles in `infra/docker/`, both multi-stage.** `jvm.Dockerfile` takes the build argument `APP` and makes the api, the scheduler and the portal: they differ only in the name of the jar, so four files would repeat the same three quarters (the plan said "a Dockerfile per app"; this is a Dockerfile per *kind* of image). `spa.Dockerfile` makes the workspace. Base images are pinned by tag, which was checked on Docker Hub on 2026-11-04: the builder is `clojure:temurin-21-tools-deps-1.12.6.1673-bookworm-slim` (with Node copied from `node:22.23.4-bookworm-slim` for the workspace), the JVM runtime `eclipse-temurin:21.0.13_9-jre-alpine-3.24` and the web server `nginxinc/nginx-unprivileged:1.30.6-alpine3.24`. The Maven cache is a BuildKit cache mount, so a change in one app does not download the world again; `.dockerignore` leaves out `.git`, `.env*`, every `node_modules` and `target`, and `design/dist`.
3. **A runtime that does as little as it can.** The JVM images run as a user that is not root, with the root file system read-only (a `tmpfs` for `/tmp`), no capabilities (`cap_drop: ALL`) and `no-new-privileges`; the JVM is PID 1 (exec form, so it gets SIGTERM and the shutdown hooks of the apps run). The options are `-XX:+UseSerialGC -XX:TieredStopAtLevel=1 -XX:-UsePerfData -XX:+ExitOnOutOfMemoryError` and a heap per service (`JAVA_OPTS`), with the limit of the container about half as large again (starting values: api 256 MB and 448 MB, scheduler and portal 192 MB and 384 MB, nginx 64 MB; they are measured with `docker stats` before the step closes). The health check of a JVM service is the `/readyz` of the app itself, with the BusyBox `wget` of the image, so that `depends_on: service_healthy` orders the start by what each service needs (the api is ready when Keycloak's keys and HAPI answer, the scheduler and the portal when the api is).
4. **The workspace is served by nginx, with a configuration made from the data of the Ring server.** `pulse.spa.nginx` (JVM, in `apps/spa`) writes `infra/spa/nginx.conf` from `pulse.spa.security` (the policy and the other headers, on every response, errors among them, `always`) and `pulse.spa.files` (the kinds of file, the name of a file that is kept for a year because it has its hash in it, the page for any path that is not a file, a 404 as a problem for a name with an extension that is not there, a 405 with `Allow` for what is not GET or HEAD, and `/healthz`); `bb spa:nginx` writes it and a test fails when the committed file is not what the generator makes, as for the realm and the theme. The page and the policy are compiled for the addresses the realm registers (`http://localhost:4000`, `http://localhost:8080`), as they are today; other addresses are a regeneration, not a build argument. The image is `nginx-unprivileged` (port 8080 inside, 3000 on the host) and has `RUN nginx -t`. **Two servers must answer alike, so one table of requests is run against both**: the cases of `files-test` (the paths, the names with an extension, the traversal attempts, the methods) become data in the test support, the JVM server answers them in the unit test and the container answers them in `bb smoke`.
5. **The compose profile `apps`, in the same `compose.yaml`.** Four services (`api`, `scheduler`, `web`, `spa`) with `profiles: [apps]`, so `bb up` and the tests of the stack are what they were. Published on 127.0.0.1 only: 3000 (workspace), 3300 (portal) and 4000 (api, for Swagger UI and `http/api.http`); the scheduler is not published, since the administrator reaches it through the api. The apps listen on `0.0.0.0` inside (`API_HOST`, `SCHEDULER_HOST`, `WEB_HOST`) and the secrets come from the `.env` that `bb up` creates, as for Keycloak, with no new variable. **The issuer and the back channel**, one block of the file that the three services share:

   | Stays as the browser sees it (`localhost`) | Goes to the service name |
   |---|---|
   | `KEYCLOAK_ISSUER`, `KEYCLOAK_AUTHORIZATION_URI`, `KEYCLOAK_END_SESSION_URI`, `WEB_BASE_URL`, `API_CORS_ORIGINS`, the addresses compiled into the workspace | `KEYCLOAK_JWKS_URI` and `KEYCLOAK_TOKEN_URI` (`http://keycloak:8080/...`), `FHIR_BASE_URL` (`http://hapi:8080/fhir`), `API_BASE_URL` (`http://api:4000`), `SCHEDULER_BASE_URL` (`http://scheduler:5000`) |

   The simulator and the reminders stay on (`SCHEDULER_SIMULATOR` and `SCHEDULER_REMINDERS` can switch them off): the profile is a demonstration, and readings and alerts that appear are what it demonstrates. **The first thing to verify, before anything else is built on it**, is that a token obtained through `keycloak:8080` carries `iss` `http://localhost:8080/realms/pulse`, as Keycloak's documentation says of a configured hostname; if it did not, the api would refuse the scheduler's token and the portal could not sign anybody in, and `hostname-backchannel-dynamic` would have to be revisited (the verifiers take the issuer as a setting, so nothing in the code would change).
6. **Tasks.** `bb build [app ...]` (the jars, without Docker), `bb apps` (`docker compose --profile apps up -d --build --wait`), `bb down` stops every profile (`--profile "*"`, so the apps are not left holding the network), `bb spa:nginx` (point 4) and `bb smoke` (point 7). `bb doctor` asks for Docker and for the memory the profile needs as advice, as it does now.
7. **How it is checked.** On the JVM, in `bb check`: the nginx file is what the generator makes and answers the table of requests as the Ring server does (the table is held to the generator's text, since there is no nginx to ask); the compose file and the Dockerfiles are held to rules (every service of the profile has a pinned image or a build, a health check, a limit of memory, a published port only on 127.0.0.1 and no literal secret; the base images carry a tag that is not `latest`; the user is not root; `.dockerignore` leaves out `.env`); and the names, ports and variables agree with the configuration of each app, `bb doctor` and the realm. With the containers up, `bb smoke`: every service is healthy and its `/readyz` says what it depends on is up (this is the issuer check of point 5, through the scheduler's token, the api's token for the scheduler and a person's token); the table of requests against the nginx container; a patient signs in at the portal and a practitioner at the workspace through Keycloak in a real browser and see their pages (the CSP and the CORS of the real thing, which is where nginx and the Ring server could differ); and, within a minute and a half, the simulator's readings and an alert are in the api. `bb web:journey`, which takes the addresses as options, is run against the containers too. `bb test:it` is what it is (the stack, with the apps in the test's own JVM) and stays the integration test of the plan's third item. `bb spa:journey` is not run against the containers: it must never look at somebody else's api (it acknowledges an alert), so it starts its own, and the smoke test covers the workspace in the containers.
8. **CI.** `ci.yml` runs `bb check` (so what the documentation says CI runs is true), with Node for the tests of the workspace. A second workflow, `integration.yml`, is not required to merge: by hand, weekly and on a push to `main`, it brings the stack up, seeds it, runs `bb test:it`, `bb spa:journey` and `bb web:journey` (X-110: the hosted runners have Chrome), builds the images, starts the profile and runs `bb smoke`, and on a failure keeps the logs of every container as an artifact.
9. **Left out, on purpose.** HTTPS and a hardened profile (X-50, X-94: Keycloak stays in `start-dev`), publishing images to a registry (Phase 10 asks the owner), AppCDS or a native image (X-44; ahead-of-time compilation took most of the win), compression and code splitting of the workspace (X-114), a scan of the images, digests instead of tags, Docker secrets, and running `bb spa:journey` against containers. The ones that deserve a row are added to the backlog.

## Alternatives considered

- **Serve the workspace with our own Ring server, in a JVM image like the others.** One implementation of the file rules, already tested by 225 checks of the journey, and one Dockerfile less. It costs another JVM (about 150 to 250 MB) to serve six static files, and "static files by nginx" is what the plan and ADR-0029 said. The price of nginx is a second implementation, which point 4 answers with a generator and one table of requests.
- **A Dockerfile per app.** Closer to the letter of the plan, with the same builder and the same runtime stage written three times.
- **Uberjars that are not compiled.** The simplest build, and 33 to 43 s before the first request on this machine, with health checks that must wait for it; the build of the compiled ones is about two minutes slower and the jar about 8 MB bigger.
- **Jib or buildpacks.** No Docker daemon needed to build the JVM images, but they do not make the workspace's image and add a plugin or a builder to carry; the Dockerfile is what a reader expects to find.
- **One container for the api, the scheduler and the portal, as `bb dev` runs them.** Saves two JVMs of memory and hides the architecture: that the scheduler is a client of the api, with its own token, is the point of ADR-0021 and ADR-0025.
- **A distroless runtime.** Smaller and with no shell, but without `wget` the health check would need a Java program or a binary of our own; Alpine's BusyBox gives both.
- **A second compose file instead of a profile.** The plan says a profile, and one file keeps `bb up`, `bb ps` and `bb logs` showing the whole system.

## Consequences

- One command runs the whole system, with the same images that the integration job builds; the issuer split, which has been a promise in the configuration since Phase 2, is exercised by a test for the first time.
- The first build of the images is slow (three ahead-of-time compilations of about three minutes and the workspace's release of about two, then cached), and every start of the profile takes the time of HAPI and of the JVMs (2 to 3 minutes). The profile asks for about 3.8 GB on top of what the machine uses, against 2.5 GB for the stack alone; the limits are the ones to tune.
- There are two servers for the workspace. They agree because of a table and a generator, and the day the table does not cover a case they will not: a rule added to `pulse.spa.files` must be added to the table, and the test that holds the generator to the data is what reminds whoever forgets.
- The release of the workspace is built inside Docker (Node, shadow-cljs and the Clojure CLI in one stage), which has not been done before: if it is slower or fragile than on the host, that is the first thing to look at.
- An ahead-of-time compiled jar cannot be reloaded at a REPL, which does not matter for a container; and a namespace compiled with a library that does not like it would show at the first start, which is why the smoke test starts every service.
- Alpine uses musl, not glibc. Nothing in the dependencies has native code, and the first start of each service says whether that holds.

## Update of 2026-11-04: what was built, and what the containers said

Built and checked on the owner's machine, with Docker Desktop (6 CPUs, 6 GB), in one session. The five choices stand; this records what the implementation settled and what it found.

1. **Jars.** `tools/build.clj` and the pure `tools/build_plan.clj` (what each app starts and what its jar must hold) make `target/api.jar`, `scheduler.jar` and `web.jar` (23 to 25 MB, 138 to 159 s each) with direct linking, which is what the start-up times of the spike were measured with. The build opens the jar it made and fails when a file of the app, the class of its main namespace or `Multi-Release: true` is missing. The api jar made by `bb build` answered `/healthz` in 7 s with a working set of 218 MB.
2. **Images.** Every tag of the decision pulled, so the tags read from Docker Hub were right. The first build took 3 min 37 s (the api), 1 min 39 s (the scheduler) and 1 min 24 s (the portal) because the layers and the Maven cache are shared, and 5 min 20 s for the workspace (`shadow-cljs release` 128 s with 0 warnings, `npm ci` 10 s); 335 MB for each JVM image and 92 MB for nginx. The release is assembled in the image with `clojure -M:spa-release` (a new alias of the root `deps.edn`: `pulse.design.spa/release!` on the JVM), which needs `design/tokens.edn` and the fonts besides the sources, because the namespace reads them when it loads; the dry run of that stage in a copy of the tree with only those files found it before Docker did.
3. **Options of the JVM.** Two variables, not one: `JAVA_FLAGS` are the image's and `JAVA_OPTS` the service's (the heap), so that a service that sets its heap does not lose the rest. Heaps and limits as decided (api 256 MB in 448 MB, scheduler and portal 192 MB in 384 MB, nginx 64 MB); with everything up the containers use about 205 MB, 145 MB, 145 MB and 12 MB, and HAPI 1 GB, Keycloak 0.6 GB and PostgreSQL 0.1 GB. The machine had 3.2 GB free before the stack and 1.1 GB with all seven containers up, so the limits could be lower and are left as they are until a longer run says otherwise.
4. **nginx.** `pulse.spa.nginx` writes the headers and the policy once at the level of the server with `always` (an `add_header` in a location replaces all those of the server), the kinds of file and their charsets, `merge_slashes off`, the rules that decide what a path is as regular expressions in the order nginx tries them, a `map` for how long a file is kept and one for `Allow`, and the 404 and 405 problems as named locations with `types {}`. `charset_types` leaves out `text/html`: nginx always sets it, and `nginx -t`, run when the image is made, warned of the duplicate. The table of requests has 45 rows; the Ring server and the container (nginx 1.30.6) answer all of them alike, and the same table applied to the portal fails all 45. What cannot be made alike is written in the file (`differences`): nginx resolves `.` and `..` itself, a bad percent-encoding is a 400, and a problem has no `instance`.
5. **The issuer.** The risk of the decision did not happen. Asked at `keycloak:8080`, the discovery document says `issuer` `http://localhost:8080/realms/pulse`, puts the token and key endpoints at `keycloak:8080` and the authorization endpoint at `localhost:8080`, and the tokens that the api's and the scheduler's containers ask for themselves say `iss` `http://localhost:8080/realms/pulse`. The api accepts the tokens of people, the scheduler accepts the api's own token (`GET /api/admin/jobs` from the administrator shows the three jobs), and the api accepts the scheduler's (the rules engine raised an alert that the practitioner finds). `KC_HOSTNAME` and `KC_HOSTNAME_BACKCHANNEL_DYNAMIC` needed no change.
6. **Tasks.** `bb build`, `bb apps` (the images one at a time, then `up -d --wait`: 65 s with the images built, the services healthy in 25 to 45 s), `bb smoke` and `bb spa:nginx`; `bb down`, `bb ps`, `bb logs` and `bb reset` use `--profile "*"`. `libs/platform/src` is on the paths of `bb.edn`, so that `bb smoke` reads the headers of the workspace from `pulse.spa.security`. `docker compose --profile apps stop` stops the infrastructure as well (a service with no profile is part of every selection), which cost one run of the integration tests against a stack that was not there; naming the services stops only the applications (X-148).
7. **`bb smoke`** passed its 24 checks on the first run, in 49 s, and `bb web:journey` its 62 against the portal's container. No container was killed or restarted and no log of an application has a warning. Not run: `docker compose --profile apps up` with no image built, which builds the four at once (X-147), and the journey of the workspace against the containers (X-146). **The containers write to HAPI** (the readings of the simulator and the alerts the rules raise from them, and the requests for a visit that the portal's journey makes), and the contract tests of `bb test:it` compare HAPI with the demo cohort as it was seeded: the first run of `bb test:it` after the containers had 14 failures (extra appointments of Ana, extra alerts), and passes again after `bb reset` and `bb seed`. So `bb test:it` goes before the containers in `integration.yml` (a test holds the order), and locally after them it needs a reset.
8. **CI.** `ci.yml` runs `bb check`; `integration.yml` is the workflow of point 8. `tools/test/workflows_test.clj` holds what can be read of both; neither has run on GitHub.
9. **Backlog.** X-144 (compression in nginx), X-145 (a scan and a bill of materials, digests), X-146 (the journey of the workspace against the containers), X-147 (build the four at once), X-148 (stop only the applications); X-110 is done and X-44 is mostly done.
