## Commands

Run from the repository root (any shell; quote the path, it has a space). Do not invent others: the remaining `bb` tasks arrive with their phase.

- `bb doctor`: checks JDK, Clojure CLI, Babashka, Node, Docker, free RAM and ports (ports in use are expected while the stack is up).
- `bb test`: Kaocha unit tests (config in `tests.edn`; tests tagged `^:integration` are skipped). Pass Kaocha args through, for example `bb test --focus pulse.fhir.reference-test/parse-examples` to run a single test, or `bb test --focus :scheduler` for a suite (`:fhir`, `:platform`, `:api`, `:scheduler`, `:web`, `:spa`, `:ui`, `:view`, `:tools`, `:design`, `:dev`). `bb test:it` runs the integration tests against the running stack (the portal's, `pulse.web-stack-test`, signs in through the real login page and needs the port 3300 free: stop `bb web` and `bb dev` first).
- `bb seed` loads the demo cohort into HAPI (idempotent, about 700 resources); `bb seed:validate` runs HAPI's `$validate` on a representative sample, `--all` on every resource.
- `bb lint` (clj-kondo), `bb fmt` (cljfmt fix), `bb fmt:check`, and `bb check` (format + lint + realm check + design check + test, what CI runs).
- Design (needs `npm ci` once in `design/`, Node only): `bb design:theme` writes `design/theme.css` from `design/tokens.edn`, `bb design:check` fails if a pair of colours is below its contrast or the theme is stale (it is part of `bb check`), `bb design:contrast` prints every ratio, `bb design:icons` and `bb design:fonts` copy the icons (as Clojure data into `libs/ui`) and the font from their npm packages, `bb design:css` compiles `design/dist/pulse.css` with Tailwind, `bb design:keycloak` writes the login theme of Keycloak (templates, messages, icon and fonts) into `infra/keycloak/themes/pulse/login` and compiles its stylesheet there (run it after a change of the tokens, of a component that the login uses or of `pulse.design.keycloak`, and commit what it writes: a test fails when a committed file is not what the generator makes), `bb design:web` writes the static files of the portal into `apps/web/resources/public` (the font and its license, the icon and htmx, copied) and compiles its stylesheet there with Tailwind from `design/css/web.css` (run it after a change of the tokens, of a component or of a page of the portal, and commit what it writes: a test fails when a committed file is not what the generator makes, or when a page uses a class that the stylesheet has no rule for), `bb design:spa` writes the static files of the clinical workspace into `apps/spa/public` (the page that loads the script, the font and the icon; not under `resources`, which is on the classpath where the portal's own `public/pulse.css` is) and compiles its stylesheet there with Tailwind from `design/css/spa.css` (run it after a change of the tokens, of a component or of a page of the workspace, and commit what it writes: a test fails when a committed file is not what the generator makes, or when a page uses a class that the stylesheet has no rule for), `bb design:build` makes the mock-ups in `design/dist` (open `index.html`), `node design/keycloak-shots.mjs [scenario ...] [--width 390] [--scheme dark]` takes screenshots of the pages that the real Keycloak serves with the theme (needs the stack; the scenarios are login, login-error, logout-confirm, signed-out, error and page-expired), and `bb design:shots [page-prefix ...] [--theme pulse-dark] [--width 390] [--clip y:height]` takes screenshots of them into `design/dist/shots` with headless Chrome or Edge (a page of the style tile at 1280 px, a mock-up as it is in its frame at each of its widths unless `--width` says one; the variable `CHROME` names the browser if it is not in the usual place).
- Stack (needs Docker and `.env`): `bb up` (creates `.env` with random secrets if missing, or adds to an existing one the variables of `.env.example` it lacks, keeping the values it has: `bb env:init` does only that; rebuilds the realm JSON, starts PostgreSQL, Keycloak and HAPI, waits for readiness), `bb down`, `bb ps`, `bb logs [service]`, and `bb reset` which **destroys the stack's data** and starts clean (about 2 minutes).
- Keycloak realm: edit `tools/realm.clj`, run `bb realm:build` and commit the generated JSON (`bb realm:check` fails if it is stale). Keycloak skips the import when the realm exists, so apply changes locally with `bb reset`. `bb realm:smoke` signs in as every demo user, through the Swagger UI client `pulse-docs` and as the service accounts of the scheduler and the api, and checks their token claims; `bb token <username|scheduler|api> [pulse-docs]` prints an access token (for REST Client's `@token`; with `pulse-docs`, the one Swagger UI would get; `api` is the api's own, which is for the scheduler and not accepted by the api).
- `bb dev [dev|lite]` runs the api (127.0.0.1:4000), the scheduler (127.0.0.1:5000) and the patient portal (127.0.0.1:3300: the sign-in, the sign-out, the home, the readings, the appointments, the record and the profile of a patient, the form to record a reading and the one to ask for a visit; it gets `WEB_CLIENT_SECRET` from `.env` as the others get theirs) in one JVM (`pulse.dev`, ADR-0023); `lite` uses an in-memory FHIR server instead of HAPI, shared by both, but still needs Keycloak. The scheduler and the api get their secrets from `.env` (`pulse.dev` reads them when the process has no `SCHEDULER_CLIENT_SECRET` or `API_CLIENT_SECRET`), and the administrator's `GET /api/admin/jobs` shows the jobs of the scheduler (the api asks the scheduler at `SCHEDULER_BASE_URL`, `http://localhost:5000`: it follows `SCHEDULER_PORT`). The scheduler simulates the devices of the cohort (about 28 readings a minute, written to FHIR, and an abnormal episode in turn: Sofía at the start, Ana after 2 minutes, Liam after 4, Maya after 6, every 8 minutes; `SCHEDULER_SIMULATOR=false` stops it), evaluates the rules every 30 seconds, so alerts appear in `/api/alerts` within a minute, and looks every minute for the confirmed appointments of the next 24 hours (`SCHEDULER_REMINDERS=false` stops it): Ana's, about 20 hours ahead in the cohort, gets its reminder, a `Communication` in FHIR, in the first minute (no endpoint of the api shows it yet; with HAPI it is seeded relative to the moment of `bb seed`, so only a recent seeding has an appointment within a day). The readings stay in the FHIR server (tagged `https://pulse.example/tag|simulated`) until `bb reset`. Logs are readable text; set `LOG_FORMAT=json` and `LOG_LEVEL=debug` for JSON lines and more detail. Try it with `http/api.http` and `bb token <user>`, or in a browser at `http://localhost:4000/docs/` (Authorize signs in as a demo user; use `localhost`, not `127.0.0.1`, which the realm's redirect addresses do not name).
- `bb scheduler [dev|test]` runs the scheduler alone (127.0.0.1:5000; with the simulator on, it takes `SCHEDULER_CLIENT_SECRET` from `.env`, which `bb up` created, and needs the stack for Keycloak). `/readyz` then says `token: up` when it has got its own token from the real Keycloak, and `api` and `fhir` up when the api (`API_BASE_URL`, default `http://localhost:4000`: run `bb dev` in another terminal) says it is ready and FHIR (`FHIR_BASE_URL`) answers. Its jobs are `evaluate-rules`, every 30 seconds (`SCHEDULER_EVALUATE_EVERY_MS`; 300000 is five minutes), which reads the patients and their readings through the api with the scheduler's own token and writes the alerts to FHIR, `simulate-devices`, every 15 seconds, and `send-reminders`, every minute (`SCHEDULER_REMINDERS_EVERY_MS`), which reads the confirmed appointments of the next 24 hours from FHIR and writes a `Communication` for each, once. The scheduler accepts only tokens whose audience is `pulse-scheduler`, which only the api's service account gets (`bb token api`: with it `/jobs` can be read, and not started), so the administrator reaches it through the api. Without the task: `clojure -M:dev -m pulse.scheduler.main`, with the variable set.
- `bb web [dev|test]` runs the patient portal alone (127.0.0.1:3300; it takes `WEB_CLIENT_SECRET` from `.env`, which `bb up` created; `WEB_PORT`, `WEB_HOST`, `WEB_BASE_URL` (the address it is served at, an origin: `http://localhost:3300`, which the realm registers; an `https://` one makes the cookie `Secure` and sends HSTS), `API_BASE_URL`, `KEYCLOAK_ISSUER`, `KEYCLOAK_JWKS_URI`, `KEYCLOAK_AUTHORIZATION_URI`, `KEYCLOAK_END_SESSION_URI` and `KEYCLOAK_TOKEN_URI` change where it listens and whom it asks). With the stack up and the api running (`bb dev` runs it too), open <http://localhost:3300> (`localhost`, not `127.0.0.1`: the realm and the cookie are of `localhost`) and sign in as `ana.garcia@pulse.test`; `dr.rivera@pulse.test` and `admin@pulse.test` are told that the portal is for patients. `/readyz` says `keycloak: up` when it can get the identity provider's keys and `api: up` when the api (`API_BASE_URL`, default `http://localhost:4000`: run `bb dev`, or `bb dev lite`, in another terminal) says it is ready; without the api it says 503 and `api: down`. Without the task: `clojure -M:dev -m pulse.web.main`.
- `bb web:journey [--portal url] [--keycloak url] [--shots dir]` is the acceptance of the patient portal in headless Chrome or Edge (the variable `CHROME` names the browser if it is not in the usual place), against the real Keycloak and the portal on 3300: start the stack (`bb up`) and `bb dev lite` first (an in-memory FHIR server, which leaves nothing behind; with `bb dev` and HAPI it leaves one reading and one cancelled request of Ana's). It reads `DEMO_USER_PASSWORD` from `.env`, prints a PASS or FAIL line for each of its 62 checks and exits with 1 if one fails; `--shots` writes a picture of each page at 390 and 1280 px in both schemes.
- `bb spa` watches and serves the clinical workspace on <http://localhost:3000> with hot reload (shadow-cljs; needs `npm ci` once in `apps/spa`; for the sign-in it needs the stack, `bb up`, and for the api `bb dev`; `localhost`, not `127.0.0.1`: the realm's redirect addresses name it). It has no Content-Security-Policy (its client needs `eval` and a WebSocket): the policy is checked on the release. `bb spa:build` makes the release in `apps/spa/target/release` (the optimized script with the hash of its content in its name, the page, the stylesheet, the icon and the font; about 0.9 MB, a minute and a half) and **fails on any warning of the compiler**, the inference ones among them. `bb spa:serve [dev | test]` serves that release on 127.0.0.1:3000 with the policy of the real thing (`pulse.spa.main`). `bb spa:test` compiles and runs the tests of the workspace on Node (shadow-cljs `:node-test`, about 50 s: part of `bb check`). On Windows the build needs `powershell` on the PATH, which `tools/spa.clj` adds when a shell lacks it (Git Bash did); without the task, `npx shadow-cljs ...` in `apps/spa` from a shell that has it.
- REPL: alias `:dev` (see `dev/repl/user.clj`), for example Calva jack-in, then `(go)`, `(reset)`, `(halt)` (Integrant; `reset` reloads with clj-reload); it starts the api and the scheduler as `bb dev` does, and needs `SCHEDULER_CLIENT_SECRET` and `API_CLIENT_SECRET` in the environment or in `.env`.
- New source directories must be added to the lint and format paths in `deps.edn`, `cljfmt.edn` and `.lsp/config.edn` (`libs`, `apps`, `tools`, `dev`, `design/src` and `design/test` already are: not `design` itself, which holds `node_modules`), and a new test directory to `tests.edn`. `bb.edn` has `libs/ui/src`, `libs/view/src`, `apps/web/src`, `apps/spa/src` and `design/src` on its paths, so `bb -e` and the tasks see them (`bb --classpath` replaces them, and the dependencies of `bb.edn` with them). `dev/repl` (the REPL's `user.clj`, which Clojure loads by itself when it is on the classpath, so it is never on the `:test` one), `dev/src` (`pulse.dev`) and `dev/test` are the three parts of `dev`. `tools` is on the `:test` classpath so that `tools/test` (the `.env` tooling, `env-test`) can load `tools/env.clj`, which uses nothing that only Babashka has; the other tools run under `bb` only.

## libs/fhir

FHIR R4 resources are plain keyword-keyed maps. Portable `.cljc`: `reference`, `coding`, `terminology` (verified LOINC/ICD-10-CM/RxNorm catalogue), `units` (UCUM as data), `ranges`, `observation` (multimethod on `value[x]`), `measurement` (the six measurements that can be recorded as data: stored unit, precision, plausible limits; `normalize` checks a submitted reading and converts it, `observation` builds the resource; [ADR-0014](docs/adr/0014-recording-and-reading-observations.md)), `appointment` (the lifecycle of an appointment as data and pure functions: `transitions`, which says who may take each action, `:by` a `:patient` or a `:clinician` and what restricts them (a patient may only cancel, and only until it begins: [ADR-0027](docs/adr/0027-a-patient-cancels-their-own-appointment-the-lifecycle-says-who-and-me-names-the-doctor.md)), `available-actions` (of an appointment, a kind of actor and the time), `request-errors`, `proposal` and `change` (of an appointment, a command, the time and the kind of actor: it answers `:ok`, `:forbidden`, `:conflict` or `:errors`, and a kind that `transitions` does not name may do nothing); [ADR-0015](docs/adr/0015-appointments-lifecycle-and-panel.md)), `alert` (`active?` and `acknowledge` for a Flag; [ADR-0016](docs/adr/0016-alerts-inbox-and-acknowledgement.md)), `resource` (builders), `schema` (malli, open maps), `outcome`, `bundle` (transactions of `PUT`s, and `conditional-create-entry`, a `POST` with `ifNoneExist` that is how an alert is raised once: [ADR-0022](docs/adr/0022-rules-engine-rules-as-data-alerts-raised-once.md); `location-id` reads the id from the `Location` of an answer), `time`. JVM/Babashka only: `client` (the `FhirClient` protocol, lazy paged search, and `create-once!`, the conditional create by the first identifier of a resource that raises an alert or sends a reminder once: it answers `{:outcome :created|:existing :id}` and refuses a resource with no identifier to go by), `client.http`, `client.memory` (a faithful fake server for tests and the "lite" profile; a conditional create answers as HAPI does: no match creates, one match is left as it is and answered with a 200, whatever its status, more than one is a 412), `synthetic` (the deterministic cohort from `resources/pulse/seed/cohort.edn`). The same code runs in the apps, the tests and `bb` (see `bb.edn` `:paths`).

Gotchas learned the hard way: malli `:re` uses `re-find`, so patterns need `^…$`; Babashka has no `StrictMath` (the generator's noise is additions only); `sequence`+`cat` and `mapcat` over `iteration` fetch extra pages (see `client/paged`); HAPI's validator runs out of its 768 MB heap under concurrent `$validate` calls (keep validation sequential); FHIR string search ignores case and accents ("Garcia" finds "García"), and `client.memory` does too; a comma is OR in a reference search (`patient=Patient/a,Patient/b`), in both clients; R4 gives `Flag` no `status` search parameter; `ranges/classify` answers nil for a unit it cannot convert, because other systems write to the same server and one odd reading must not fail a series. A server gives the resource of a conditional create its own id, so the entry has none; the condition is a query string and is encoded like any other (`c/query-string`: an identifier value holds slashes and colons). Several creators of the same resource at once store one on HAPI (tested with six, never two), but it answers most of the others with a 409, not a 200, and `create-once!` does not retry. The in-memory client must reject whatever HAPI rejects: contract tests against HAPI compare answers and check that every search parameter the fake declares exists on HAPI. `client.http` has request and connect timeouts (`java.net.http.HttpTimeoutException`, a 504 in the api).

## libs/platform

JVM only; the mechanisms shared by the services, with no policy of their own. `config` (Aero + malli: `read-config` validates before anything starts, and never prints the offending values; its `#csv` reader turns a comma-separated value into a set, and its `#secret` reader wraps a value in a `Secret` that prints as `#secret[REDACTED]` wherever it ends up, Integrant's dump of a failed component included, and is opened with `reveal`; `*environment*` lets a test say what a variable is for `#env`, so that a profile that needs one can be tested on every machine), `log` (Telemere, [ADR-0010](docs/adr/0010-structured-logging-with-telemere.md)), `jwt` (the access-token verifier, [ADR-0009](docs/adr/0009-access-token-verification-with-nimbus-facade.md): `verify` returns `{:ok claims}` or `{:error {:type ...}}` and never throws because of a bad token; `errors` and `challenge` give the status and `WWW-Authenticate`), and `http/*` ([ADR-0011](docs/adr/0011-api-request-pipeline-and-errors.md)): `problem` (RFC 9457 errors), `middleware` (request id, access log, exception handler), `auth` (bearer authentication), `health` (readiness checks under one deadline), `cors` (an allow-list of exact origins, the preflight answered before the router, never `*` and never credentials; [ADR-0018](docs/adr/0018-cors-and-security-headers.md)), `headers` (security headers on every response, with a rule per path prefix where `nil` removes a default) and `router` (the Reitit setup of a JSON service: `options` with content negotiation and malli coercion, `default-handler` and `exception-handlers` for what the router does not know and the failures with a meaning of their own, and `endpoints-without`, the traversal behind deny by default; [ADR-0020](docs/adr/0020-scheduler-executor-and-http-surface.md)); `system` (the Integrant components every service starts the same way, `:pulse.platform/logging`, `jwks`, `verifier`, `server`, `token-source` and `service-client`, which a service's keys `derive` from, with the schemas of their configuration); `http/client` (a client of another Pulse service that sends the caller's own token: `request` returns `{:status :body}` whatever the status and takes `:headers` besides (the api sends its request id to the scheduler in `X-Request-Id`; `Authorization`, `Accept` and `Content-Type` are the client's own and cannot be changed), `get-json`/`post-json` throw an `::http/failed` with the `:status` and the problem the service gave, an `::http/unreachable` with a `:reason` of `:connect` or `:timeout`, or the `::token/unavailable` of the keeper; `path` encodes each segment, `query-string` encodes a map and writes a plus as `%2B`); `token` (an access token from the token endpoint, [ADR-0021](docs/adr/0021-service-tokens-client-credentials-cached-and-renewed-early.md): `endpoint` is the POST to the token endpoint of one client as a function of a form, made once with its HTTP client, which the client-credentials grant of a service and the authorization-code and refresh grants of the portal all use, and returns the grant with the `:refresh-token` and the `:id-token` as `Secret`s; `source` and `access-token`, lazy with no thread, renewed early on a call, one caller asks while the others use the token they have, never an expired one, and an `::unavailable` with a `:reason` when there is none to be had; `source` takes `:initial`, a grant in hand with the `:asked-at` of the request that got it, and is a record that prints as `#token-source[client]`, so that a keeper in the data of an exception never prints its token); and `fanout` (named tasks run at once on virtual threads under one deadline, [ADR-0013](docs/adr/0013-patient-summary-fan-out.md)). Since Phase 7, step 3: the client `request` sends no `Authorization` header when it has no keeper in its `:token` (the portal's client of the api has none of its own: each call is `(assoc client :token keeper-of-the-session)`, and readiness asks the public `/readyz` with none), and never sends one that a caller put in `:headers`; `middleware/wrap-exceptions` takes `:unexpected`, `(fn [request])` for the response to a failure nobody expected (a service whose answers are pages and not problems, such as the portal, gives its page; the cause is logged all the same); `headers/origin-of` (the origin of an address, for a policy that names the identity provider) and `router/allow-header` are public; `system/client-schema` is the schema of a client with no token of its own, beside `service-client-schema`.

## apps/api

Resource server and FHIR gateway on Ring + Jetty + Reitit. `pulse/api/config.edn` (classpath resource) is the Integrant system map, read by Aero and checked by `pulse.api.config/schema` (closed maps, so a misspelt key fails); profile `dev`, `lite` or `test`, chosen with `API_PROFILE`. `system` starts the components (logging, jwks, verifier and server are the platform's, by `derive`), `handler` assembles the pipeline (the router setup is the platform's `http/router`), `routes` is the route table as data, `identity` turns verified claims into an identity (its role list must match the realm: a test compares it with the committed realm JSON), `fhir` is how the api reads FHIR (a failure becomes a 502, a slow server a 504, `find-one` fetches one page, `search` is capped, `put!` writes), `times` reads the times of requests (and holds the schemas of the fields that carry them), and `patients`, `summary`, `observations`, `appointments`, `alerts` and `me` are the endpoints. `docs` generates the OpenAPI 3.1 document from the route data (`reitit-openapi`), completes each operation from what the data says elsewhere (`:authz` gives the security requirement, `x-pulse-access` read from `authz/rules` and the shared 400, 401, 403, 404 and 5XX problems; `:problems` gives an endpoint's own 409 and 422, with when) and serves Swagger UI under `/docs` ([ADR-0017](docs/adr/0017-api-documentation-openapi-and-swagger-ui.md)); `security` is the policy of the response headers: the Content-Security-Policy of the api, and the one `/docs` needs ([ADR-0018](docs/adr/0018-cors-and-security-headers.md)). The pipeline, outermost first: request id, access log, security headers, CORS, exception handler, router; the handler of `/docs` comes before the router's own 404. The configuration has `:issuer` (the identity provider as a browser reaches it, where the sign-in of Swagger UI goes; it refers to the verifier's) and `:cors {:allowed-origins ...}` (`API_CORS_ORIGINS`: exact origins separated by commas, never `*`; by default the workspace's `http://localhost:3000`).

Authorization is `authz` ([ADR-0012](docs/adr/0012-authorization-by-scope.md)): `rules` is Annex A as data, each role's *scope* per action (`:own`, `:panel`, `:all`, `:identifiers`); `authorize`, `scope-of` and `permits?` are pure; the middleware authenticates, asks, audits and attaches `:identity`, `:scope` and the `:descriptor` (what the endpoint's `:resource` function built, which may carry the resource itself so that a change works on the version the decision was about). `audit` holds the two audit events: `:pulse.audit/access` for every decision and `:pulse.audit/write` for a write FHIR has accepted (who, the action, the patient and the resource reference, never a value). Every endpoint declares `:authz` (`:public`, or `{:action a}` with a rule for `a`, plus `:resource (fn [request scope])` on an endpoint for one resource); `check-routes!` makes the start-up fail otherwise (deny by default, ADR-0004 and ADR-0011). A collection endpoint restricts its own FHIR query to the scope; it never fetches everything and filters afterwards. `summary` (the latest reading of each of the six measurements that can be recorded, the temperature included since Phase 7, step 6, so that a patient finds again what they recorded) fans about a dozen FHIR queries out at once (`pulse.platform.fanout`: virtual threads, one deadline, [ADR-0013](docs/adr/0013-patient-summary-fan-out.md)); a section that fails or is late is `null` and named in `unavailable`, never silently empty. `observations` ([ADR-0014](docs/adr/0014-recording-and-reading-observations.md)) is the series (`measurement`, `from` inclusive, `to` exclusive, `limit`, `truncated`; no offsets) and the recording of a reading: 400 from the schema for the shape, 422 from `measurement/normalize` and the time window for what cannot be a reading, the server deciding subject, performer, status, id and time; `reading-view` is also the summary's latest vital sign. `appointments` ([ADR-0015](docs/adr/0015-appointments-lifecycle-and-panel.md)) is the list by scope, a patient's request (always to their general practitioner) and a clinician's command (`confirm`, `reschedule`, `cancel`): 400 for the shape, 422 from `pulse.fhir.appointment` for times that cannot be right, 409 when the status does not allow the action. For an appointment the panel is the appointments the practitioner takes part in, and `PATCH` reads the appointment once, through the descriptor. A patient may also `cancel` their own appointment, a request at any time and a booked one until it begins ([ADR-0027](docs/adr/0027-a-patient-cancels-their-own-appointment-the-lifecycle-says-who-and-me-names-the-doctor.md)): the route lets the patient in with the scope `:own` (`:appointment/manage`) and the lifecycle says what each kind of person may do (`actor-kind`: a practitioner or the administrator is a `:clinician`, anyone else the `:patient`); a command that kind may not take is a 403 with a generic text, audited as a denial that names the command (`audit/access!` takes a `:change`), judged after the shape of the body (400) and before the status (409); and an appointment that does not exist is a 404 for a patient too, now. `me` also answers a patient's `generalPractitioner` (the reference, the name as the clinic writes it, the specialty), one more read, a 502 as the Patient's read is. `alerts` ([ADR-0016](docs/adr/0016-alerts-inbox-and-acknowledgement.md)) is the inbox of a panel (the panel of patients first, then their flags with an OR list of references, 50 patients at a time, and an empty panel asks nothing; `status` is applied afterwards because R4 has no such parameter for Flag) and the acknowledgement of one alert (409 when it is not active); the rules engine raises alerts by writing to FHIR, so the cohort has none and the tests raise their own. Time comes from a `:clock` among the route deps (the tests fix it). To add an endpoint: the route (with `:tags`, `:summary`, `:description`, a `:description` for each response and `:problems` for a 409 or a 422), the schemas (a `:description` on each parameter and field), `:authz`, a rule if the action is new, and tests: the Annex A table is in `authz-test`, and the table of operations with their statuses is in `docs-test`, which also fails for a missing description.

The status of the jobs ([ADR-0025](docs/adr/0025-job-status-through-the-api-its-own-service-account-and-a-role-for-it.md)): `jobs` is `GET /api/admin/jobs`, for the administrator (the rule `:jobs/read`). The api is a client of the realm: `pulse-api` is a confidential client whose service account has the role `api-service` and a token for the audience `pulse-scheduler` and not for `pulse-api`, so the api would not accept its own (`:pulse.api/token`, the secret `API_CLIENT_SECRET` as a `#secret`; `:pulse.api/scheduler`, at `SCHEDULER_BASE_URL`). It asks the scheduler's `GET /jobs` with that token, never the caller's, and carries its request id in `X-Request-Id`. What the scheduler answers is checked against the api's own schema (`m/validate`, which is open) before it goes on, and the response coercion then strips what the api does not declare. A scheduler that cannot be reached, refuses the token, fails or answers something else, and an api that cannot get its own token, are a 502, a scheduler that is too slow a 504; the text is generic and the cause is in the log. A failure that is not one of those three kinds (a bug) is a 500 and not a 502 that blames the scheduler. `/readyz` does not ask the scheduler. The `dev` and `lite` profiles cannot start without `API_CLIENT_SECRET`, which `bb env:init` adds to an `.env` that lacks it; the realm needs `bb reset` once to have the client. Tests: `jobs-test` against a stand-in for the scheduler (what the api sent, what it answered, every way to fail), `pulse.dev-test` with both services in one JVM and the fake identity provider answering each its own token, and `pulse.dev-stack-test` (integration) with the real Keycloak, where the audience and the roles of the realm keep each token to the service it is for.

Tests: `apps/api/test-support` holds the harness (`pulse.api.test.harness`: fake identity provider, in-memory FHIR with the demo cohort, tokens for the demo people, `call`, a FHIR `spy`; `with-api` takes `:cors-origins` and `:scheduler`); `docs-test` and `security-test` check the document, Swagger UI, the headers and CORS through the whole handler; `stack-test` runs the api against the real stack with `bb test:it`, the sign-in of Swagger UI among it.

Gotchas learned the hard way: reitit-malli closes every `:map` schema and strips undeclared keys, so a FHIR resource in a response schema must be `[:map-of :keyword :any]` (a plain `:map` turned it into `{}`); malli does not apply defaults to `:optional` keys, so a parameter with a default is declared required with `:default` on its value schema; Reitit adds an `OPTIONS` endpoint to every route unless `::ring/default-options-endpoint` is nil; query parameters are only parsed if `parameters-middleware` is in the chain; muuntaja is restricted to JSON. In a query string a `+` is a space, so an offset such as `+02:00` must be sent as `%2B02:00` (the tests use `enc`); a `:fn` schema carries the message of a 400 (`:error/message`), and the explanation of an `:and` lists every failing child (a `:min` next to the `:fn` gave two messages, so the length is left to the `:fn`); the `:test` alias has Kaocha's `:main-opts`, so a scratch script needs the `:dev` alias; Kaocha captures standard output (a `println` in a test shows only if the test fails); test.check's `gen/let` has no `:let`, and `gen/double*` clusters near zero (use `gen/choose` to spread numbers over a range); a property test on an endpoint that changes state must create a new resource for every sample, or most samples meet a final state and are 409s (tally the statuses a generator produces before trusting it); the shape of a body is judged before the status of the resource, so a body that is wrong is a 400 even when the status would have been a 409; clj-kondo wants `Duration/ZERO`, not `(Duration/ZERO)`.

The document and the headers: the artifact is `fi.metosin/reitit-openapi` (not `metosin/`), and `ring-swagger-ui` 5.32.11, which `reitit-swagger-ui` pulls, lacks `oauth2-redirect.js` (the api pins 5.33.0); `reitit.ring/router` sets its own `:coerce` (private), so the documentation is derived from the routes of the finished router; `reitit-openapi` overwrites `components.schemas` with the schemas it found, so the shared `Problem` is added after it; malli's `:json-schema` property replaces the generated JSON Schema (a `:fn` is otherwise `{}`), a `:multi` default branch becomes an overlapping `oneOf` alternative (word the error with `:error/message` on the `:multi` instead), and a parameter with a `:default` is required for the coercion and marked not required by `docs`; a response with no `:description` makes the document invalid. Swagger UI takes the OAuth client and PKCE only from `initOAuth` (our `swagger-initializer.js`, served by name), and its sign-in popup needs `window.opener`: never set `Cross-Origin-Opener-Policy` on `/docs`. Reitit's resource handler matches by prefix and ignores the method (`docs/ui-handler` guards both; ring refuses `..`), and ring serves `.js` as `text/javascript`. The policy of `/docs` was checked in headless Chrome over the DevTools protocol (a Node script with no dependencies, not in the repository: extra X-47): a control that must be blocked, such as an inline script, has to be seen by the check before "no violations" means anything.

## apps/scheduler

Under construction (Phase 5): the schedule, the executor, the HTTP surface, the rules engine, the device simulator and the reminders are done; the catalogue of jobs (`pulse.scheduler.jobs/catalogue`) holds `evaluate-rules`, `simulate-devices` and `send-reminders`, and what is left of the phase is the api's side of the status of the jobs (step 7). `pulse/scheduler/config.edn` is the Integrant system map, read and checked like the api's (profile `dev` or `test`, chosen with `SCHEDULER_PROFILE`; closed maps). `schedule` ([ADR-0019](docs/adr/0019-scheduler-jobs-as-data-and-a-pure-next-run.md)): a schedule is EDN, either `{:type :interval :every-ms n}` (optionally `:offset-ms`; the grid is counted from the epoch, so when the process started changes nothing) or `{:type :daily :at "HH:mm[:ss]" :zone "Europe/Madrid"}`; `schema`, `valid?` and `problems` are what the configuration will be checked with, and `next-run` is pure: the first instant strictly after the one given, with no clock and no state. `job` is `{:id :description :schedule :handler}` (the id is a simple lower-case keyword, because it will go in URLs) and `check!` validates a catalogue, ids unique.

`executor` ([ADR-0020](docs/adr/0020-scheduler-executor-and-http-surface.md)): the ticks fire on one daemon thread (`ScheduledThreadPoolExecutor`) and the handlers run on virtual threads named `job-N`. A tick first arms the next tick, for `next-run` asked from the later of now and its own moment, and then runs the job unless it is still running (that tick is skipped, counted and logged): so a job never overlaps itself, a pause or a long run is not made up for, and the chain of ticks outlives a handler that fails or hangs (handlers must be safe to repeat). The state is one atom with a map for each job, changed by `swap!`, so claiming a run is atomic. `status` and `job-status` are data; `run-now!` answers `:started`, `:already-running`, `:unknown-job` or `:stopped` and does not move the schedule; `stop!` ends the ticks, waits `:grace-ms` for the handlers and interrupts the rest. A handler takes `{:job-id :trigger :due :started-at}` and returns nil or a map of simple values; an interruption is an `InterruptedException` anywhere in the cause chain; the status shows the class of an error and never its message. The clock, the tick scheduler and the workers are parameters, which is how the tests drive time by hand: `pulse.scheduler.test.time` (in `apps/scheduler/test-support`) has `world`, `advance!`, `fire-next!`, `set-time!` and `direct-workers`, and real virtual threads with a promise as a gate are used where two things must happen at once.

The HTTP surface is a second resource server, built like the api's without CORS: `authz` (`rules` as data from action to roles, `:jobs/read` for `clinic-admin` and `api-service`, the api's own service account, and `:jobs/run` for `clinic-admin` alone; deny by default through `check-routes!`; `:pulse.audit/access` events of the shape the api's have), the verifier's audience `pulse-scheduler` (a token meant for the api is a 401 here, and the other way round), `routes` (`/healthz`, `/readyz`, `GET /jobs`, `POST /jobs/{id}/run` that answers 202, 404, 409 or 503; the views are camelCase with ISO strings), `handler` and `security`. `pulse.scheduler.test.harness` (`with-scheduler`, `token-for`, `call`) wires the handler to a fake identity provider and an executor in fake time. `GET /api/admin/jobs` in the api calls it with the api's own service-account token (ADR-0025). The scheduler's own token comes from `:pulse.scheduler/token` (client `pulse-scheduler`, the secret from `SCHEDULER_CLIENT_SECRET` as a `#secret`, `KEYCLOAK_TOKEN_URI` for the address inside a container); nothing is asked of Keycloak until a token is needed, and `/readyz` has a `token` check, so a wrong secret shows as unready and not as jobs that fail. The dev profile cannot load without the variable, so the tests read it with `*environment*` set. `/readyz` also asks the api (`GET /readyz`, with the scheduler's token) and FHIR; the status of a job shows the keys of its result in camelCase.

The rules engine ([ADR-0022](docs/adr/0022-rules-engine-rules-as-data-alerts-raised-once.md)): `rules` (`defrule` defines a var holding a rule's data and its condition twice, as the function that runs and as the quoted form of the same text, checked against a schema when the namespace loads; `evaluate` is a pure multimethod on `:recent-count`, `:window-count` and `:rise`, from a rule, readings and `now` to nil or `{:readings :newest-at}`; readings go in a total order, by time and then by their numbers, because a server does not order those of one instant; a rise is compared in rationals, since 64.1 − 62.1 is 1.999999999999993 in doubles; `query` says what to ask the source for, from a second before the look-back), `alerts` (the Flag of a rule, a patient and the newest reading that supports it, identified as `R1/pt-ana/2026-10-13T08:00:00Z`; `raise!` is `c/create-once!`, a conditional create in a one-entry transaction, so an alert that exists, active or acknowledged, is left as it is; `active?` finds the active alert of a rule and a patient by the prefix `R1/pt-ana/`, with its slash, so that `pt-ana-2` is not `pt-ana`), `source` (`DataSource`; `ApiSource` reads the patients and the series through the api with the scheduler's token and the active conditions from FHIR, because Annex A gives `rules-engine` neither the patient nor the summary; `reading-from-item` puts an item in the stored unit and drops one that cannot be used, so that one odd reading does not stop the others) and `engine` (`run!` goes patient by patient and returns a summary; `failure/fatal?` (shared with the reminders) says which failures end the run: an interruption, no token, the api or FHIR unreachable or failing, the api refusing the token; a patient that fails is counted and logged; an alert raised is a `:pulse.audit/write` event with the scheduler's client as the actor). `jobs/catalogue` builds `evaluate-rules` from the components when it is `:enabled?` (not in the tests); a run with failed patients throws, so that it shows as a failed run. Tests: `rules-test` (the macro and what it expands to, the examples of Annex C with their boundaries, properties), `alerts-test`, `source-test` against a stand-in for the api, `engine-test` (the cohort seeded at each hour of the day, against a source read from the cohort and FHIR in memory) and `end-to-end-test`, which serves the api's own handler with Jetty and runs the engine against it: the four alerts of Annex C, raised once, an acknowledgement kept, and a patient's token refused with a 403. The harness (`with-scheduler`) takes `:fhir` and has a stand-in for the api whose answer a test changes through `:api-answer`.

The device simulator ([ADR-0023](docs/adr/0023-device-simulator-core-async-pipeline-to-a-fhir-transaction.md)): `simulator` (`scenario` makes the devices out of the signals of the cohort and the settings in `resources/pulse/scheduler/simulation.edn`, and fails at the start when they are wrong; `plan` is a pure function of the scenario, the number of the tick and its instant: a device is due every second tick at its own turn, its reading is the baseline of the signal at that hour of the day with a noise that is drawn again if it is further than 2 standard deviations, so that a normal reading cannot cross a threshold of Annex C, and an *episode* of the settings takes over its signal for the ticks it lasts: one for each rule, in a cycle of 32 ticks; `observation` is what the api makes of a reading, `measurement/normalize` and `measurement/observation`, with no performer, a `device` and the tag `https://pulse.example/tag|simulated`, under an id made of the patient, the signal and the second; `tick!` sends a plan through the pipeline) and `pipeline` (generic: a producer thread puts a lazy sequence on a bounded channel, `pipeline` runs the transducers keeping the order, a `partition-all` transducer on a channel makes the batches and flushes the last, one writer thread, not a `go` block since it does blocking I/O, writes each; a batch that fails is counted and logged and the next go on; an interruption or a timeout closes the source, gives what is in the pipeline `:drain-ms` to be written, and throws an ex-info of type `::interrupted` or `::timeout` with the stats, the first with the `InterruptedException` as its cause, which is how the executor knows it). The job `simulate-devices` counts its ticks from the start of the scheduler, so the first episode begins with it, and fails if a reading could not be made or written. The tests apply the rules to 70,000 normal readings (none may satisfy a condition, and no weight may rise 2 kg), run each episode through its rule (it must fire on at least two ticks in a row, that is for 30 seconds, since the engine runs every 30), and `pulse.dev-test` is the acceptance of the phase: the real systems of the api and the scheduler in one JVM, the simulator's readings seen by the api, the alert raised and found in the inbox of the practitioner.

The appointment reminders ([ADR-0024](docs/adr/0024-appointment-reminders-a-communication-sent-once-from-what-fhir-holds.md)): `reminders` (`query` is the search for the booked appointments that begin after `now` and no later than the window after it, in whole seconds so that HAPI and the fake agree to the second; `reminder-key` is `<appointment id>/<start in UTC>`, so an appointment that moves gets a new reminder; `practitioner-name` is the given and family names with no title; `message` is the text, in English whatever the language of the machine and in the zone of the clinic, `Reminder: your appointment with Elena Rivera is on Wednesday 14 October at 06:00 (Hypertension follow-up).` (the formatter is made in each call so that a test can change the default locale and see that it makes no difference); `communication` is the completed reminder with the identifier and no id; `run!` makes one search of the clinic and a `c/create-once!` for each appointment, reads each doctor once for the run, and returns `{:appointments :sent :already-sent :failed}`; an appointment that fails is counted and logged, `failure/fatal?` ends the run, and a reminder sent is a `:pulse.audit/write` event with the action `:reminder/write` and the rule `R5`, never the text). `failure` holds `fatal?`, which the engine had as a private function; it now also says that an interruption ends a run, since a handler must not swallow one (ADR-0020). The job `send-reminders` (settings `:window-hours`, 1 to 168, and `:zone`; `SCHEDULER_REMINDERS` and `SCHEDULER_REMINDERS_EVERY_MS`) reads and writes FHIR and not the api, so it works with the api down, and fails if a reminder could not be sent. Tests: `reminders-test` (the edges of the window to the second, the text through the days the clocks change and with the language of the machine changed, one reminder for each appointment and time, a failure of one appointment and one of the infrastructure, the audit, the cohort hour by hour, and a property against an oracle), `failure-test`, `stack-test` (HAPI and the fake remind the same patients, and HAPI finds the reminders valid) and, in `pulse.dev-test`, the acceptance: in the full system the cohort's appointment of Ana is reminded once.

Gotchas learned the hard way: a property test that shuffles must generate the permutation (`gen/shuffle`), or a failure cannot be repeated or shrunk; the `:test` classpath (`clojure -Spath -A:test`, plus the test directories) run with `clojure.main` and `clojure.test/run-tests` takes about 18 seconds against 70 through Kaocha, and a loop of hundreds of runs in one JVM is how a failure of one run in sixty was found (two readings of one instant gave an answer that depended on their order) and what makes mutation analysis affordable: each mutated source is evaluated in that one JVM (`load-string` of the mutated text, nothing written to disk, so a killed run leaves no file mutated) and the test namespaces are reloaded after it, because they capture rules and protocols at load time (a `defprotocol` is made anew by the reload, so a `reify` of it must be too); a JVM for each of the 250 mutations of step 4 would have taken hours, and a file mutated on disk and then left by a killed run had to be put back by hand. The tests of step 4 were strengthened by what it found: boundaries of the windows and of the status codes that end a run, readings of one instant, the encoding of a name in a query, the form of a `Location`. `engine/run!` excludes `clojure.core/run!` in its `ns`. HAPI answers a conditional create with a 201 and the `Location` `Flag/123/_history/1`, or a 200 for the one that was there; the condition is a query string and goes encoded. A stub server that records requests must record the raw path, or an encoded segment looks like what it was meant to be. A system test that enables a job with its real schedule can have the job fire in the middle of it (a 15-second interval did, one run in ten): give the jobs a test runs by hand a schedule of a week, which the epoch grid makes fire on Thursdays at midnight UTC. A search of the in-memory client is lazy and each page is computed from the state at that moment, so deleting while walking it skips resources: realize it first (`doall`). In bash `((` starts an arithmetic expression, so a group of commands that begins with two parentheses is not one. A function of `pulse.fhir.client` is mutated as a copy of itself evaluated with `in-ns`, because evaluating the whole file makes the protocol `FhirClient` anew and leaves the clients that were loaded with the old one. `t/with-signals` returns a throw as its `:error` and does not throw it. `(.plus instant n unit)` with an `n` that comes from a `range` is reflection: `(long n)`. Gotchas of the schedule and the executor: a daily time that the clocks skip runs right after the gap, and one they repeat runs the first time (`ZonedDateTime/of` does both); `next-daily` tries the days from one before to two after the date of `after`, and both ends are real: Greenland's clocks go from 23:00 to 00:00 (since 2024), so the 23:30 of a day comes out at 00:30 on the next date, and Newfoundland's went back at 00:01 to 23:01 (until 2010), so the next day's 00:00 had already happened. Mutation checks found that a random zone and moment never reach either (a range of two days survived), so the tests build cases from every such change in the JDK's time zone database and count that they get there; the daily property tests compare with an oracle that walks the minutes (valid for times without seconds in zones with whole-minute offsets); a scratch script that needs the test directory runs with `clojure -Sdeps '{:paths ["apps/scheduler/test"] :deps {org.clojure/test.check {:mvn/version "1.1.3"}}}' -M:dev script.clj` (the `:test` alias would run Kaocha). A `reify` of an overloaded method (`schedule` of a `ScheduledExecutorService`) must name the return type on the method (`(^ScheduledFuture schedule ...)`), and one with a hinted parameter and a single match must name it too (leave the hints off `execute`). A `ScheduledThreadPoolExecutor` keeps an exception thrown by a task in its future and says nothing, so a tick catches everything and arms the next tick first. `executor/stop!` waits (2 s) for the thread of the ticks after `shutdownNow`, and only then shuts the workers down: before, `isTerminated` of the scheduler could still be false when `stop!` returned, which failed `the-real-pools-run-a-job-and-stop-in-order` about once in 80 runs (a loop of 150 runs of that test alone found it; `bb check` found it under load). `with-redefs` on a private function works through its var (`executor/claim!`) and is how a failing tick is simulated. `bound-fn*` carries Telemere's log context to another thread, which is how a manual run's events keep the request id. The threshold of a generator-coverage test is set from the measured mean and spread, not a round number below it (100 against a mean of 122 failed one run in fifty). A test that waits for a job to be idle and then reads what its worker logged races: the state is set before the event is logged; look at what the worker saw from inside it (`t/*ctx*` in the handler). A deftype needs `equals` and `hashCode` for two readings of the same file to be equal configurations (`Secret`).

## apps/web

The patient portal ([ADR-0028](docs/adr/0028-the-patient-portal-a-server-side-client-of-the-api-with-its-own-sign-in-and-a-token-keeper-for-each-session.md)): pages rendered on the server, a client of the api. **Phase 7 is done: the skeleton (step 3), the sign-in, the session, the sign-out and the renewal (step 4), the home (step 5), the readings and recording one (step 6), the appointments (step 7), and the record, the profile and the acceptance (step 8).** `pulse/web/config.edn` is the Integrant system map, read by Aero and checked by `pulse.web.config/schema` (closed maps; profile `dev` or `test`, `WEB_PROFILE`): `logging`, `jwks` (the identity provider's keys: readiness asks for them), `access-verifier` and `id-verifier` (two `:pulse.platform/verifier`s: the access token is for the audience `pulse-api` with `typ` Bearer, the id token for `pulse-web` with `typ` ID), `api` (the portal's client of the api, a `:pulse.platform/service-client` with no token), `oidc` (the portal as the client `pulse-web` of the realm: `WEB_CLIENT_SECRET` as a `#secret` that the dev profile cannot start without, `WEB_BASE_URL`, the addresses of Keycloak as the browser reaches them and as the portal does, and the timeouts), `sessions` (the limits of the store), `handler` and `server` (`WEB_HOST`, `WEB_PORT` 3300; the redirect address of the client in the realm is `http://localhost:3300/oauth2/callback` and its post-logout addresses `http://localhost:3300/*`, and a test compares them). `pulse.web.system` starts them, `main` is `bb web`, and `pulse.dev` starts the portal with the api and the scheduler (its client of the api comes after the api's server).

`handler` assembles the pipeline, outermost first: request id, access log, security headers (HSTS when `WEB_BASE_URL` is https), exceptions (`wrap-exceptions` with `:unexpected errors/server-error`), the check of the origin (`csrf/wrap-origin`), the session (`session/wrap-session`) and the router (Reitit, with no content negotiation: `authz/middleware`, `parameters-middleware` and `csrf/middleware`). What the router does not know is `errors/default-handler` (404, and 405 with `Allow`: the page "We cannot find that page"). `routes` is the route table as data and every route says `:authz :public` or `:authz :patient`: `authz/check-routes!` stops the start-up for one that says neither. A `:patient` route gives its page to whoever `(:person (:session request))` is; anyone else is sent to `/sign-in?return-to=...` with a 303 (a browser that comes with the cookie of a session that is not there gets the page "Your session has ended", 401, and drops the cookie), or, for a request of htmx (`HX-Request: true`), a 401 with `HX-Redirect` so that htmx leaves the page and never puts a sign-in in a fragment. A handler of such a route asks the api with `(assoc api-client :token (session/tokens-of request))`, and when the keeper cannot give a token `authz` answers for it: refused by the identity provider (`oidc/rejected?`, also while it is backing off) ends the session and says so, anything else is "Sign-in is not available right now" (503) and the session stays. The place to come back to (`return_to`) is a path of this server and nothing else: one slash and printable ASCII, no backslash, 2000 characters at most; for a GET it is the page with its query, for htmx the page the request came from (`HX-Current-URL`), for any other method the home page. Public: `/healthz`, `/readyz` (JSON: `keycloak` is whether the keys can be had and `api` whether the api's own public `/readyz` answers 200, asked with no credentials), `/assets/*path` (`assets`: GET and HEAD, only a name of plain segments and a known extension, from `resources/public` on the classpath, with `Cache-Control: no-cache` and a 304 when it has not changed), `/sign-in`, `/oauth2/callback` and `/signed-out`; for a patient, `/` (the home), `/readings` (the trend of a measurement), `/readings/new` (the form to record a reading: a GET and a POST), `/appointments` (the appointments, and a POST that asks for a visit), `/appointments/{id}/cancel` (a GET that asks the question and a POST that answers it), `/record` (the medication, the conditions and the allergies), `/profile` (who the patient is to the clinic, their doctor and the way out) and `POST /sign-out`.

The sign-in is the portal's own authorization-code flow (`signin`, `oidc`): `/sign-in` makes a pending sign-in (`state`, PKCE verifier, `nonce` and the place to come back to, kept on the server in a new entry under a new key) and sends the browser to Keycloak (`scope openid profile`); `/oauth2/callback` compares the `state` with the pending one in constant time (`values/same?`: two values that are not there are not equal) and asks Keycloak nothing otherwise, **takes the pending sign-in out of the store atomically** (`session/consume!`, so that two identical callbacks cannot both exchange the code, which would make Keycloak take back the tokens of the first), exchanges the code, verifies both tokens and the `nonce` and that they are of the same person, and lets in only a person with the role `patient` (anyone else gets "This portal is for patients", 403, a link that signs out at Keycloak, which asks first, no session, and an audit event `:pulse.audit/access` with the action `:portal/sign-in` and `:denied`); the session is a new entry holding `{:person {:id :username :name} :tokens <keeper> :csrf <token>}`. What goes wrong is a page in the portal's words (`pages/error-kinds`: "That sign-in has expired", "We could not sign you in", "Sign-in is not available right now", with the cause and never the provider's words in the log). `POST /sign-out` (with the CSRF token) ends the session first and then sends the browser to Keycloak's end-session address with `id_token_hint` (the last id token the keeper was given) and `post_logout_redirect_uri` `/signed-out`. `oidc/keeper` is a `pulse.platform.token/source` started with the grant of the code exchange (`:initial`) that renews with the refresh grant, keeping the refresh token each renewal gives and the last id token (`oidc/id-token`, a `Secret`); a renewal that Keycloak refuses while the access token is still good is not told to the person, who works until it expires.

`session` is Ring's `SessionStore` in memory with what Ring's own lacks: a signed-in session ends after 30 minutes without a request or 10 hours after the sign-in, a pending sign-in after 10 minutes, there are at most 1 000 pending sign-ins (the oldest goes, never a session) and 10 000 sessions (the one least recently used goes), a key is 256 bits and one the browser chose is never used, a write that changes the kind of an entry is a new entry, and it prints how many entries it holds and never what. The cookie is `pulse-session`, `HttpOnly`, `SameSite=Lax`, a session cookie, `Secure` when the address is https. `csrf`: the check of the `Origin` for every request that changes something (a present `Origin` that is not the portal's is refused, `null` too) and, for the routes of a patient, the CSRF token made at the sign-in, read from the form field `__anti-forgery-token` or the header `X-CSRF-Token` by `ring-anti-forgery` with a strategy that reads it from the session (its own would make a session for a visitor that only asked for a page). `audit` has the shape of the api's audit events.

`pages` is pure hiccup with no Ring, so Babashka loads it for the mock-ups: `document` (the stylesheet, the icon and htmx as files of the portal, the `htmx-config` meta tag before its script: no eval, no script in an answer, no `<style>` of its own, only this server, and `historyCacheSize` 0 so that no page of a patient's record is kept in the storage of the browser; `:csrf-token` puts the token in `hx-headers` on the body), `error-kinds` (the four of the mock-up the owner approved, in its words, and the five of the sign-in, which the review page of the errors shows for the owner to approve), `error-card` and `error-page` (the card in a frame, with its title as the `h1`), `signed-out-page`, `sign-out-form` (a POST with the token, which takes the address to post to: the profile has it as a button of its own besides the menu's), `csrf-field`, `nav` (the five pages of the mock-up: Home, Readings, Appointments, My record and Profile) and `page` (the frame of a page of a patient: the document, the bar, the dock and the menu, where the person signs out with a button of a form that carries the CSRF token; no button for the theme, X-93); `html` writes a page as a response. `security` is the policy: `default-src 'self'` and the rest of ADR-0028, with `form-action 'self'` plus the origin of the identity provider (signing out is a form that Keycloak answers with a redirect, and Chrome applies `form-action` to a redirect), and the headers: `Cache-Control: no-store`, `Referrer-Policy: same-origin` (not `no-referrer`, with which a browser sends `Origin: null` with a form it posts to its own server), the cross-origin ones and HSTS for an https address. The static files (`resources/public`: the stylesheet, htmx 2.0.11, the font with its license, the icon) are made by `bb design:web` and committed.

## design

The design system ([ADR-0026](docs/adr/0026-design-system-as-data-tokens-theme-components-and-contrast-by-test.md)). `design/tokens.edn` is the source: the palette (teal, chosen by the owner on 2026-10-16 from three candidates, in light and dark: the themes are called `pulse` and `pulse-dark`; with several palettes and none selected the generator writes a theme for each, as the style tile did), the neutrals, the tones of a reading, the colours of a chart, type, shape, shadows, and the list of pairs of colours that need a contrast. `tools/design.clj` is pure (it runs under Babashka and on the JVM): it checks the tokens with malli (closed maps), measures the WCAG contrast of every pair of every palette in both schemes (a ratio is shown cut at two decimals, never rounded, so 4.4994 is 4.49:1 and cannot read as the minimum) and writes `design/theme.css`: the daisyUI themes (`@plugin "daisyui/theme"`, and none of daisyUI's own), custom properties `--pulse-*` for what daisyUI has no variable for (muted text, the border of a control, the tones, the colours of a chart: they switch with the theme), `@theme inline` that makes them Tailwind colours (`bg-tone-normal-soft`, `text-muted`, `stroke-series-1`) and the `@font-face` of Inter. `design/css/input.css` is Tailwind's entry (`base.css`, the generated theme and the `@source` paths: `libs/ui/src`, `apps/web/src` and `design/src`) and `bb design:css` compiles it into `design/dist/pulse.css` (Tailwind 4.3.3 and daisyUI 5.7.50, pinned in `design/package.json`); `design/css/base.css` is written in no layer, so it wins over daisyUI's rules: the border of a field is the token `control-border` (3:1; daisyUI's own is 20 % of the text colour, about 1.5:1), the focus ring and reduced motion. Inter is in `design/fonts` with its license (committed; `bb design:fonts` copies it from the npm package), and the icons listed in `design/icons.edn` are Lucide (ISC; MIT for those derived from Feather).

The mock-ups: `design/src/pulse/design/` has `data` (the synthetic cohort at 14:00 on Tuesday 13 October 2026, so that the appointments fall on working days, in the shapes of the api: a test compares each with the api's own `reading-view`, `view` and schema), `format` (only what the workspace says of the scheduler: an interval, a schedule, a duration; the times, numbers and units of every interface are `pulse.view.format`), `specimen` (a reading as a tile and as a chart: the usual range of each measurement, the lines of the rules, the normal band), `chrome` (the frame of the review pages: a bar with the links in menus by group, and a theme select that `design/assets/review.js` remembers between pages; `listed` leaves out the pages that say `:listed? false`), `tile` and `catalogue` (the pages of the style tile), `views` (what a page shows of an appointment, an alert or a patient: view models made from the data, the order of urgency of a panel, the headline reading of a patient; `rule-descriptions` are the words of the rules, and a test compares them with `pulse.scheduler.rules`), `mockup` (a mock-up of an interface is two documents: its frame, `frames/<page>.html`, which is the interface itself with no trace of the review, and the page of the review around it, with an iframe the width of a phone (390 px), a tablet (820) or a desk (1280), so that the page answers to the width it is given and `review.js` makes the frame as high as the page in it), `signin`, `portal` and `workspace` (the mock-ups: the persona of the portal is Ana García, who has very high readings, and Noah Kim, who has none; that of the workspace is Dr. Elena Rivera and her four patients, and Sam Admin for the jobs; each page is a function of the context of the build that returns the document of its frame), `pages` (the registry: a style-tile page has `:render`, a mock-up has `:frame`, `:devices`, `:summary` and `:notes`), `build` (`documents` is every file written: a page, or a page and its frame), `shotplan` (which screenshots, as a pure function the tests hold: the frame of a mock-up at each of its widths, in both themes), `shots` (the browser) and `icons`. What the cohort does not hold (the alerts, the jobs, two appointments of Ana) is written by hand in `data` in the shapes of the api and checked against its schemas; what a page offers is held to what the system can do (the buttons of an appointment are `appointment/available-actions`, the limits of a reading are `measurement`'s, nobody is said to have been told of a reading, no visit "took place", no editing of a profile). `bb design:build` renders the pages to `design/dist` and fails when a page uses a class the compiled stylesheet has no rule for (a misspelling, or a class that is not written whole); `design/dist` and `design/node_modules` are ignored by git. `data-theme="pulse-dark"` on any element shows its subtree in that theme, and `?theme=` in the address picks the theme of the page. `design/shots.mjs` takes the screenshots with headless Chrome or Edge over the DevTools protocol with no dependency (Node has a WebSocket client of its own): `--headless=new --remote-debugging-port=0` writes the port to `DevToolsActivePort` in the profile directory.

The login theme of Keycloak: `pulse.design.keycloak` makes the theme `pulse` (its `parent` is `base`, which has the markup of every page and no stylesheet) in `infra/keycloak/themes/pulse/login`, which `compose.yaml` mounts into Keycloak and the realm names as its `loginTheme`: `theme.properties`, `template.ftl` (the layout every page calls as the macro `registrationLayout`, with the sections of the page nested in it: `header`, `subtitle`, `form`, `socialProviders`, `info` and `show-username`), the pages the realm uses (`login`, `error`, `info`, `logout-confirm` and `login-page-expired`), `messages/messages_en.properties`, the icon and, copied from `design/fonts`, the font; `resources/pulse.css` is compiled by Tailwind from `design/css/keycloak.css` (the base rules and the theme of the interfaces, and only the classes that the templates and `theme.properties` use, about 41 KB). The templates are FreeMarker made from hiccup: `ftl` is raw text that hiccup does not escape, `msg` the interpolation of a message, and `when-ftl` and `either-ftl` the conditionals. `messages` is the English of the theme, written to `messages_en.properties` and read by the mock-ups through `message` (so what is reviewed is what Keycloak shows), and `base-messages` the words of Keycloak's own that a template asks for and the theme does not reword. The pages that the theme does not rewrite (a new password, a one-time code) keep the markup of `base` and get the classes of `class-properties` through `theme.properties`. `check` finds what a committed file lacks or has too much of, `write!` writes. Tests: `keycloak-test` (the files: committed is what the generator makes, no file nothing makes, the properties, the messages, a rule in the stylesheet for every class, the colours of the tokens, the fonts, the icon, the realm and `compose.yaml`), `keycloak-render-test` (the templates filled in by FreeMarker 2.3.32, which Keycloak 26.0.0 ships, configured as Keycloak configures it, with a model of what Keycloak gives a page, read back by `pulse.ui.test.html` and put through `pulse.ui.test.a11y`, branch by branch, with what a person typed escaped, and the parts and the words of each page compared with the mock-up; `pulse.design.test.freemarker` is the harness: a map with strings for keys becomes a hash, a vector a sequence and a function a method, and `render` answers the HTML and the keys of the messages it asked for) and, with `bb test:it`, `keycloak-stack-test` (the same pages from the real Keycloak, and the stylesheet, fonts and icon it serves, byte for byte). `bb token` and `bb realm:smoke` sign in through the form of this theme: `tools/loginpage.clj` reads its address whatever the order of the attributes.

Gotchas of the login theme: Hiccup writes attributes in alphabetical order and escapes `& < > " '` in their values, so FreeMarker inside an attribute is written as two variants inside an `<#if>`, and a regular expression that expects `id` before `action` fails; every `<#nested>` writes the white space around it, so the sections of a page are on the one line of the macro call, and `<#local x><#nested "subtitle"></#local>` with `x?has_content` is how a page with no subtitle leaves no empty paragraph; Keycloak's `msg` is a MessageFormat (an apostrophe in a message swallows the braces after it) that gives the key back when it has no message; what `kcSanitize` returns is a string that `?no_esc` lets through, and what `${...}` writes of anything else is escaped, because a `.ftl` is HTML; Tailwind reads `theme.properties` as text, and in `kcFormGroupClass=mb-5 flex` the first class is joined to the name, so the properties are written with ` = `; Keycloak gives relative addresses (`/realms/...`) on some pages and absolute ones on others, so resolve them against the page; `java.net.CookieManager` refuses the cookies of `localhost`, which has no dot (the test of the real Keycloak keeps them itself); `start-dev` does not cache themes and the directory is mounted, so a regenerated theme is there on the next request; a parameter of the Write and Edit tools turns ` ` into the character and `sed` takes `\u` for a case switch, so a character that needs an escape is written `(char 0xA0)`; `with-redefs` of a function with one that calls the original needs the original captured first, or it is a stack overflow.

Gotchas learned the hard way: Tailwind 4 does not read files that git ignores, so every source that writes classes is an explicit `@source`, and `dist` must not be one; daisyUI puts its components in a layer, so an override has to be unlayered; in daisyUI 5 `--input-color` is both the border of an unchecked checkbox, radio or toggle and the fill of a checked one, so use the `-primary` variants (the unchecked border is then the brand colour, which has the contrast); `border-l-4` shifts the content by 3 px, and an edge bar inside a box with `overflow-hidden` does not; Inter's figures need `tabular-nums` to line up (the page of the type shows both); `bb --classpath` replaces the paths and dependencies of `bb.edn`; a `cd` in one Bash call stays for the next one, so quote the whole path or `cd` to the root in every call; a heredoc with an apostrophe in a Bash call can fail to parse, and a `node -e` string eats backslashes: write Clojure files with the Write tool. The usual range of each measurement (heart rate 40 to 140, glucose 50 to 300, ...) is the domain of its chart, wider than the data, so that a normal reading looks flat inside the green band and one away from it looks like it. Of the mock-ups: a frame is as high as its page, so `position: fixed` is relative to that height (a dialog is in the middle of the page and a toast in a corner nobody sees: the toast was deleted, X-85); a row of a list that must wrap its buttons needs a basis on its text (`basis-44`), because a flex item that can shrink never makes its neighbour wrap; a `table` of a chart is in a `<details>` inside its figure, so a test that wants the table of readings finds the chart's first (find it by its caption); the sidebar link `Appointments` has the `aria-label` of the list `Appointments`, so find a list by `:ul` and its label; `with-redefs` of `data/latest` changes `data/vitals` too, which calls it for every measurement; `pulse.design.pages` captures the page functions when it loads, so a mutation run of a page namespace must reload it as well; a daisyUI `dialog` with `modal-open` is `position: fixed`, so its page behind it is as tall as the page.

The files of the portal: `pulse.design.web` makes the static files of `apps/web/resources/public` as `pulse.design.keycloak` makes the theme (`files`: the icon, which is the login theme's; `copied-files`: the font and its license, from `design/fonts`; `htmx`, copied from `design/node_modules/htmx.org` and checked to be the version that `design/package.json` pins, which must be exact; `check` and `write!`), and `design/css/web.css` is its stylesheet's entry (`libs/ui/src` and `apps/web/src` as sources, and the rules of `.htmx-indicator` that htmx would write as a `<style>`, which the policy of the pages forbids): `bb design:web`. The mock-up `errors` of the portal is made of `pulse.web.pages/error-card` and `parts/not-loaded`, and `portal-home` and `portal-new-patient` of `pulse.web.pages.home/content` (`bb.edn` has `apps/web/src` on its paths for it): what is reviewed is what is served (ADR-0028). For that `pulse.design.data` has `me`, `summary` and `series`, what the api answers a patient, which a test holds to the handlers of the api over the same cohort (equal for every patient and measurement, apart from what is written by hand: two appointments and an alert), and `portal/home-model` and `portal/links` give the page what it is a function of. Of step 6: `portal-readings` and `portal-new-reading` are `pulse.web.pages.readings/content` and `pulse.web.pages.reading-form/content` (`portal/readings-model` and `portal/new-reading-model`, the second being the form as the api's refusal of a diastolic of 310 leaves it, in the words the portal writes of it; `data/series` takes a period, `{:from :to :limit}`, and a test holds it to the api's own for every patient and measurement), and `specimen/line-chart` is `pulse.view.charts/line-chart` made from the cohort, so that the style tile and the workspace did not change. ## Local stack

Everything binds to 127.0.0.1: Keycloak 8080 (management/health 9000), HAPI FHIR 8090 (`/fhir`, `/actuator/health`), PostgreSQL 5432. About 1.5 GB of RAM in total. Demo users and their password come from `tools/realm.clj` and `.env` (`DEMO_USER_PASSWORD`). Keycloak shows its sign-in in the theme `pulse`, mounted read-only from `infra/keycloak/themes/pulse` (the realm names it as `loginTheme`): `start-dev` does not cache themes, so after `bb design:keycloak` a refresh of the page is enough, with no `bb reset`. HAPI has no container healthcheck (distroless JRE); `bb up` polls it from the host. HAPI caches searches for about a minute (send `Cache-Control: no-cache` when testing). After days of idling, the first search of HAPI can take longer than the 2-second deadline of the readiness of the api, which then says `fhir: down` (once, in `the-api-against-the-real-stack` of `bb test:it`): run the tests again. Right after a `bb reset` its validator is cold, and a `$validate` in `bb test:it` can fail with "Regex evaluation timed out" (once, in `every-reading-the-api-can-record-is-a-valid-observation-on-hapi`): run the tests again.

## What it is

Remote patient monitoring and appointment coordination on FHIR R4 with Keycloak SSO. Four apps of different kinds share one realm (`pulse`) and one FHIR server (HAPI): `api` (resource server and FHIR gateway), `web` (server-rendered patient portal), `spa` (ClojureScript clinical workspace) and `scheduler` (rules engine and simulator).

## Working agreements

- Everything written in the repository is in English: code, comments, UI text, docs, ADRs, commit messages. The conversation with the owner is in Spanish.
- Document first: a stack or architecture change gets a short ADR (`docs/adr/`, created in Phase 1) before the code.
- The names used by the original proof of concept must not reappear anywhere in the repository (code, config, docs, comments, sample data).
- Data is synthetic only. No secrets in git: use `.env` (ignored) and commit `.env.example`.
- Do not install software, change Windows/WSL/Docker configuration, start containers, publish to GitHub, make commits or permanently delete files without the owner's explicit confirmation at that moment. Send removals to the Recycle Bin or an archive first.

## Fixed decisions

- Keycloak stays at **26.0.0** (keycloak-js on the 26.0.x line) with Keycloak's default password hashing. No custom hash provider.
- FHIR R4 on HAPI FHIR with a pinned image tag; resources use deterministic client-assigned IDs (`PUT`).
- Terminologies: LOINC, ICD-10-CM, RxNorm and UCUM. No SNOMED CT.
- Clojure 1.12.x on JDK 21 (shadow-cljs 3 requires JDK ≥ 21). UI: Tailwind CSS 4 + daisyUI 5.

## Workstation (Windows 10; PowerShell and Git Bash)

- The Clojure CLI is the `clj-msi` build (deps.clj, `clojure --version` prints "Clojure CLI version (deps.clj)") in `%LOCALAPPDATA%\Apps\clojure`. Babashka comes from winget. npm is 11.21 (npm 12 needs Node ≥ 24.15 and the machine has 24.12). `JAVA_HOME` is set at user level.
- Processes started before Phase 0 (VS Code, its terminals, agent shells) do not see the new `PATH`. If `clojure` or `bb` is not found, restart VS Code or prepend `%LOCALAPPDATA%\Apps\clojure` and the Babashka winget package folder to `PATH`.
- shadow-cljs (the clinical workspace) starts the Clojure CLI, which on this machine (deps.clj) starts `powershell`: from Git Bash, or any shell whose PATH lacks `C:\Windows\System32\WindowsPowerShell\v1.0`, it fails with "Executable 'powershell' not found". The `bb spa*` tasks add the directory; a direct `npx shadow-cljs` from the PowerShell tool needs `$env:PATH = "C:\Windows\System32\WindowsPowerShell\v1.0;" + $env:PATH` first. The first compile takes 75 to 105 s, a hot reload less than a second.
- Docker Desktop is capped by `~/.wslconfig` at 6 GB and 6 CPUs. Free RAM is scarce (about 0.7 GB with Docker idle), so do not start the full stack casually.
- The project path contains a space (`Clojure Porfolio`): always quote paths.
- In PowerShell, `"text $var: more"` is parsed as a scope-qualified variable and fails; write `${var}:`.
- In Git Bash, prefix `docker exec`/`docker cp` that use container paths with `MSYS_NO_PATHCONV=1`, or `/tmp/x` becomes a Windows path.
- Double quotes inside an argument that Java hands to `bb.exe` (`clojure.java.shell/sh`) are lost on Windows: a test that runs `bb -e` writes the expression without them, such as `(env/get-var (name :SCHEDULER_CLIENT_SECRET))`.
- `babashka.http-client` has no cookie jar and Cheshire's pretty printer emits CRLF on Windows (see `tools/kc.clj` and `tools/realm.clj`).
