# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Status

Pulse is a portfolio project built from scratch in phases. **Phases 0 to 4 are done (workstation, foundations, infrastructure, FHIR core and seed data, and the `api` app: access-token verification, authorization by scope, the endpoints of Annex B, OpenAPI with Swagger UI and a PKCE sign-in, CORS and security headers); Phase 5, the `scheduler`, is under way (steps 1 to 6 of 7 are done: jobs as data and the pure `next-run`, ADR-0019, the executor with its HTTP surface, ADR-0020, the service token, ADR-0021, the rules engine, ADR-0022, the device simulator, ADR-0023, and the appointment reminders, ADR-0024), and `GET /api/admin/jobs`, which proxies it, comes with it (step 7).** The endpoints are `/healthz`, `/readyz`, `/api/me`, `/api/patients`, `/api/patients/{id}`, `/api/patients/{id}/summary`, `/api/patients/{id}/observations` (a GET for a series, a POST to record a reading), `/api/appointments` (a GET and a POST) with `/api/appointments/{id}` (a PATCH), and `/api/alerts` (a GET for the inbox) with `/api/alerts/{id}/ack` (a POST); the document of the api is at `/openapi.json` and Swagger UI at `/docs/`. The code so far is `libs/fhir` (FHIR data model, schemas, clients, synthetic cohort), `libs/platform` (config, logging, token verification, HTTP mechanisms, shared components), `apps/api`, `apps/scheduler` (the schedule, the executor and its HTTP surface, the rules engine, the device simulator and the reminders, its three jobs) and the infrastructure tooling in `tools/`.

## Commands

Run from the repository root (any shell; quote the path, it has a space). Do not invent others: the remaining `bb` tasks arrive with their phase.

- `bb doctor`: checks JDK, Clojure CLI, Babashka, Node, Docker, free RAM and ports (ports in use are expected while the stack is up).
- `bb test`: Kaocha unit tests (config in `tests.edn`; tests tagged `^:integration` are skipped). Pass Kaocha args through, for example `bb test --focus pulse.fhir.reference-test/parse-examples` to run a single test, or `bb test --focus :scheduler` for a suite (`:fhir`, `:platform`, `:api`, `:scheduler`). `bb test:it` runs the integration tests against the running stack.
- `bb seed` loads the demo cohort into HAPI (idempotent, about 700 resources); `bb seed:validate` runs HAPI's `$validate` on a representative sample, `--all` on every resource.
- `bb lint` (clj-kondo), `bb fmt` (cljfmt fix), `bb fmt:check`, and `bb check` (format + lint + realm check + test, what CI runs).
- Stack (needs Docker and `.env`): `bb up` (creates `.env` with random secrets if missing, rebuilds the realm JSON, starts PostgreSQL, Keycloak and HAPI, waits for readiness), `bb down`, `bb ps`, `bb logs [service]`, and `bb reset` which **destroys the stack's data** and starts clean (about 2 minutes).
- Keycloak realm: edit `tools/realm.clj`, run `bb realm:build` and commit the generated JSON (`bb realm:check` fails if it is stale). Keycloak skips the import when the realm exists, so apply changes locally with `bb reset`. `bb realm:smoke` signs in as every demo user, and through the Swagger UI client `pulse-docs`, and checks their token claims; `bb token <username|scheduler> [pulse-docs]` prints an access token (for REST Client's `@token`; with `pulse-docs`, the one Swagger UI would get).
- `bb dev [dev|lite]` runs the api (127.0.0.1:4000) and the scheduler (127.0.0.1:5000) in one JVM (`pulse.dev`, ADR-0023); `lite` uses an in-memory FHIR server instead of HAPI, shared by both, but still needs Keycloak. The scheduler gets its secret from `.env` (`pulse.dev` reads it when the process has no `SCHEDULER_CLIENT_SECRET`), simulates the devices of the cohort (about 28 readings a minute, written to FHIR, and an abnormal episode in turn: Sofía at the start, Ana after 2 minutes, Liam after 4, Maya after 6, every 8 minutes; `SCHEDULER_SIMULATOR=false` stops it), evaluates the rules every 30 seconds, so alerts appear in `/api/alerts` within a minute, and looks every minute for the confirmed appointments of the next 24 hours (`SCHEDULER_REMINDERS=false` stops it): Ana's, about 20 hours ahead in the cohort, gets its reminder, a `Communication` in FHIR, in the first minute (no endpoint of the api shows it yet; with HAPI it is seeded relative to the moment of `bb seed`, so only a recent seeding has an appointment within a day). The readings stay in the FHIR server (tagged `https://pulse.example/tag|simulated`) until `bb reset`. Logs are readable text; set `LOG_FORMAT=json` and `LOG_LEVEL=debug` for JSON lines and more detail. Try it with `http/api.http` and `bb token <user>`, or in a browser at `http://localhost:4000/docs/` (Authorize signs in as a demo user; use `localhost`, not `127.0.0.1`, which the realm's redirect addresses do not name).
- `bb scheduler [dev|test]` runs the scheduler alone (127.0.0.1:5000; with the simulator on, it takes `SCHEDULER_CLIENT_SECRET` from `.env`, which `bb up` created, and needs the stack for Keycloak). `/readyz` then says `token: up` when it has got its own token from the real Keycloak, and `api` and `fhir` up when the api (`API_BASE_URL`, default `http://localhost:4000`: run `bb dev` in another terminal) says it is ready and FHIR (`FHIR_BASE_URL`) answers. Its jobs are `evaluate-rules`, every 30 seconds (`SCHEDULER_EVALUATE_EVERY_MS`; 300000 is five minutes), which reads the patients and their readings through the api with the scheduler's own token and writes the alerts to FHIR, `simulate-devices`, every 15 seconds, and `send-reminders`, every minute (`SCHEDULER_REMINDERS_EVERY_MS`), which reads the confirmed appointments of the next 24 hours from FHIR and writes a `Communication` for each, once. The scheduler accepts only tokens whose audience is `pulse-scheduler`, which no client of the realm gets before step 7 of Phase 5, so its `/jobs` cannot be called from outside yet. Without the task: `clojure -M:dev -m pulse.scheduler.main`, with the variable set.
- REPL: alias `:dev` (see `dev/repl/user.clj`), for example Calva jack-in, then `(go)`, `(reset)`, `(halt)` (Integrant; `reset` reloads with clj-reload); it starts the api and the scheduler as `bb dev` does, and needs `SCHEDULER_CLIENT_SECRET` in the environment or in `.env`.
- New source directories must be added to the lint and format paths in `deps.edn`, `cljfmt.edn` and `.lsp/config.edn` (`libs`, `apps`, `tools` and `dev` already are), and a new test directory to `tests.edn`. `dev/repl` (the REPL's `user.clj`, which Clojure loads by itself when it is on the classpath, so it is never on the `:test` one), `dev/src` (`pulse.dev`) and `dev/test` are the three parts of `dev`.

## libs/fhir

FHIR R4 resources are plain keyword-keyed maps. Portable `.cljc`: `reference`, `coding`, `terminology` (verified LOINC/ICD-10-CM/RxNorm catalogue), `units` (UCUM as data), `ranges`, `observation` (multimethod on `value[x]`), `measurement` (the six measurements that can be recorded as data: stored unit, precision, plausible limits; `normalize` checks a submitted reading and converts it, `observation` builds the resource; [ADR-0014](docs/adr/0014-recording-and-reading-observations.md)), `appointment` (the lifecycle of an appointment as data and pure functions: `transitions`, `available-actions`, `request-errors`, `proposal`, `change`; [ADR-0015](docs/adr/0015-appointments-lifecycle-and-panel.md)), `alert` (`active?` and `acknowledge` for a Flag; [ADR-0016](docs/adr/0016-alerts-inbox-and-acknowledgement.md)), `resource` (builders), `schema` (malli, open maps), `outcome`, `bundle` (transactions of `PUT`s, and `conditional-create-entry`, a `POST` with `ifNoneExist` that is how an alert is raised once: [ADR-0022](docs/adr/0022-rules-engine-rules-as-data-alerts-raised-once.md); `location-id` reads the id from the `Location` of an answer), `time`. JVM/Babashka only: `client` (the `FhirClient` protocol, lazy paged search, and `create-once!`, the conditional create by the first identifier of a resource that raises an alert or sends a reminder once: it answers `{:outcome :created|:existing :id}` and refuses a resource with no identifier to go by), `client.http`, `client.memory` (a faithful fake server for tests and the "lite" profile; a conditional create answers as HAPI does: no match creates, one match is left as it is and answered with a 200, whatever its status, more than one is a 412), `synthetic` (the deterministic cohort from `resources/pulse/seed/cohort.edn`). The same code runs in the apps, the tests and `bb` (see `bb.edn` `:paths`).

Gotchas learned the hard way: malli `:re` uses `re-find`, so patterns need `^…$`; Babashka has no `StrictMath` (the generator's noise is additions only); `sequence`+`cat` and `mapcat` over `iteration` fetch extra pages (see `client/paged`); HAPI's validator runs out of its 768 MB heap under concurrent `$validate` calls (keep validation sequential); FHIR string search ignores case and accents ("Garcia" finds "García"), and `client.memory` does too; a comma is OR in a reference search (`patient=Patient/a,Patient/b`), in both clients; R4 gives `Flag` no `status` search parameter; `ranges/classify` answers nil for a unit it cannot convert, because other systems write to the same server and one odd reading must not fail a series. A server gives the resource of a conditional create its own id, so the entry has none; the condition is a query string and is encoded like any other (`c/query-string`: an identifier value holds slashes and colons). Several creators of the same resource at once store one on HAPI (tested with six, never two), but it answers most of the others with a 409, not a 200, and `create-once!` does not retry. The in-memory client must reject whatever HAPI rejects: contract tests against HAPI compare answers and check that every search parameter the fake declares exists on HAPI. `client.http` has request and connect timeouts (`java.net.http.HttpTimeoutException`, a 504 in the api).

## libs/platform

JVM only; the mechanisms shared by the services, with no policy of their own. `config` (Aero + malli: `read-config` validates before anything starts, and never prints the offending values; its `#csv` reader turns a comma-separated value into a set, and its `#secret` reader wraps a value in a `Secret` that prints as `#secret[REDACTED]` wherever it ends up, Integrant's dump of a failed component included, and is opened with `reveal`; `*environment*` lets a test say what a variable is for `#env`, so that a profile that needs one can be tested on every machine), `log` (Telemere, [ADR-0010](docs/adr/0010-structured-logging-with-telemere.md)), `jwt` (the access-token verifier, [ADR-0009](docs/adr/0009-access-token-verification-with-nimbus-facade.md): `verify` returns `{:ok claims}` or `{:error {:type ...}}` and never throws because of a bad token; `errors` and `challenge` give the status and `WWW-Authenticate`), and `http/*` ([ADR-0011](docs/adr/0011-api-request-pipeline-and-errors.md)): `problem` (RFC 9457 errors), `middleware` (request id, access log, exception handler), `auth` (bearer authentication), `health` (readiness checks under one deadline), `cors` (an allow-list of exact origins, the preflight answered before the router, never `*` and never credentials; [ADR-0018](docs/adr/0018-cors-and-security-headers.md)), `headers` (security headers on every response, with a rule per path prefix where `nil` removes a default) and `router` (the Reitit setup of a JSON service: `options` with content negotiation and malli coercion, `default-handler` and `exception-handlers` for what the router does not know and the failures with a meaning of their own, and `endpoints-without`, the traversal behind deny by default; [ADR-0020](docs/adr/0020-scheduler-executor-and-http-surface.md)); `system` (the Integrant components every service starts the same way, `:pulse.platform/logging`, `jwks`, `verifier`, `server`, `token-source` and `service-client`, which a service's keys `derive` from, with the schemas of their configuration); `http/client` (a client of another Pulse service that sends the caller's own token: `request` returns `{:status :body}` whatever the status, `get-json`/`post-json` throw an `::http/failed` with the `:status` and the problem the service gave, an `::http/unreachable` with a `:reason` of `:connect` or `:timeout`, or the `::token/unavailable` of the keeper; `path` encodes each segment, `query-string` encodes a map and writes a plus as `%2B`); `token` (a service's own access token with the client-credentials grant, [ADR-0021](docs/adr/0021-service-tokens-client-credentials-cached-and-renewed-early.md): `source` and `access-token`, lazy with no thread, renewed early on a call, one caller asks while the others use the token they have, never an expired one, and an `::unavailable` with a `:reason` when there is none to be had); and `fanout` (named tasks run at once on virtual threads under one deadline, [ADR-0013](docs/adr/0013-patient-summary-fan-out.md)).

Tests mint tokens with throwaway RSA keys and serve the JWKS from a local HTTP server: that fake identity provider is `pulse.platform.test.idp` in `libs/platform/test-support`, on the classpath of the `:test` alias and shared by the suites; `pulse.platform.test.stub` is a stand-in for another service (an HTTP server on a free port that answers as a function says and keeps the raw requests), and `pulse.platform.test.clock` a clock the tests move by hand. `bb test:it` also verifies tokens from the real Keycloak (it runs `bb token`).

Gotchas learned the hard way: Nimbus 10 enables refresh-ahead caching by default (a background thread; switched off explicitly); its JWKS rate limiter lets two fetches through per window and then throws `RateLimitReachedException`, which must not be reported as an unknown key when no key set was ever fetched; Keycloak's JWKS also holds an encryption key (`use: enc`) that must never verify a signature; Keycloak access tokens carry the application role next to its own default roles in `realm_access.roles`. Telemere's `:json` output format exists only in ClojureScript (we pass jsonista as `:pr-fn`); `t/with-signals` returns `{:value :error :signals}` and, with `true` as first argument, traps the signals so tests print nothing; `telemere-slf4j` is the SLF4J provider but the SLF4J API comes from Jetty. `fanout/run` runs its tasks on virtual threads and carries the caller's bindings (the log context) over. `integrant/repl` 0.5 reloads with clj-reload, not tools.namespace.

## apps/api

Resource server and FHIR gateway on Ring + Jetty + Reitit. `pulse/api/config.edn` (classpath resource) is the Integrant system map, read by Aero and checked by `pulse.api.config/schema` (closed maps, so a misspelt key fails); profile `dev`, `lite` or `test`, chosen with `API_PROFILE`. `system` starts the components (logging, jwks, verifier and server are the platform's, by `derive`), `handler` assembles the pipeline (the router setup is the platform's `http/router`), `routes` is the route table as data, `identity` turns verified claims into an identity (its role list must match the realm: a test compares it with the committed realm JSON), `fhir` is how the api reads FHIR (a failure becomes a 502, a slow server a 504, `find-one` fetches one page, `search` is capped, `put!` writes), `times` reads the times of requests (and holds the schemas of the fields that carry them), and `patients`, `summary`, `observations`, `appointments`, `alerts` and `me` are the endpoints. `docs` generates the OpenAPI 3.1 document from the route data (`reitit-openapi`), completes each operation from what the data says elsewhere (`:authz` gives the security requirement, `x-pulse-access` read from `authz/rules` and the shared 400, 401, 403, 404 and 5XX problems; `:problems` gives an endpoint's own 409 and 422, with when) and serves Swagger UI under `/docs` ([ADR-0017](docs/adr/0017-api-documentation-openapi-and-swagger-ui.md)); `security` is the policy of the response headers: the Content-Security-Policy of the api, and the one `/docs` needs ([ADR-0018](docs/adr/0018-cors-and-security-headers.md)). The pipeline, outermost first: request id, access log, security headers, CORS, exception handler, router; the handler of `/docs` comes before the router's own 404. The configuration has `:issuer` (the identity provider as a browser reaches it, where the sign-in of Swagger UI goes; it refers to the verifier's) and `:cors {:allowed-origins ...}` (`API_CORS_ORIGINS`: exact origins separated by commas, never `*`; by default the workspace's `http://localhost:3000`).

Authorization is `authz` ([ADR-0012](docs/adr/0012-authorization-by-scope.md)): `rules` is Annex A as data, each role's *scope* per action (`:own`, `:panel`, `:all`, `:identifiers`); `authorize`, `scope-of` and `permits?` are pure; the middleware authenticates, asks, audits and attaches `:identity`, `:scope` and the `:descriptor` (what the endpoint's `:resource` function built, which may carry the resource itself so that a change works on the version the decision was about). `audit` holds the two audit events: `:pulse.audit/access` for every decision and `:pulse.audit/write` for a write FHIR has accepted (who, the action, the patient and the resource reference, never a value). Every endpoint declares `:authz` (`:public`, or `{:action a}` with a rule for `a`, plus `:resource (fn [request scope])` on an endpoint for one resource); `check-routes!` makes the start-up fail otherwise (deny by default, ADR-0004 and ADR-0011). A collection endpoint restricts its own FHIR query to the scope; it never fetches everything and filters afterwards. `summary` fans about a dozen FHIR queries out at once (`pulse.platform.fanout`: virtual threads, one deadline, [ADR-0013](docs/adr/0013-patient-summary-fan-out.md)); a section that fails or is late is `null` and named in `unavailable`, never silently empty. `observations` ([ADR-0014](docs/adr/0014-recording-and-reading-observations.md)) is the series (`measurement`, `from` inclusive, `to` exclusive, `limit`, `truncated`; no offsets) and the recording of a reading: 400 from the schema for the shape, 422 from `measurement/normalize` and the time window for what cannot be a reading, the server deciding subject, performer, status, id and time; `reading-view` is also the summary's latest vital sign. `appointments` ([ADR-0015](docs/adr/0015-appointments-lifecycle-and-panel.md)) is the list by scope, a patient's request (always to their general practitioner) and a clinician's command (`confirm`, `reschedule`, `cancel`): 400 for the shape, 422 from `pulse.fhir.appointment` for times that cannot be right, 409 when the status does not allow the action. For an appointment the panel is the appointments the practitioner takes part in, and `PATCH` reads the appointment once, through the descriptor. `alerts` ([ADR-0016](docs/adr/0016-alerts-inbox-and-acknowledgement.md)) is the inbox of a panel (the panel of patients first, then their flags with an OR list of references, 50 patients at a time, and an empty panel asks nothing; `status` is applied afterwards because R4 has no such parameter for Flag) and the acknowledgement of one alert (409 when it is not active); the rules engine raises alerts by writing to FHIR, so the cohort has none and the tests raise their own. Time comes from a `:clock` among the route deps (the tests fix it). To add an endpoint: the route (with `:tags`, `:summary`, `:description`, a `:description` for each response and `:problems` for a 409 or a 422), the schemas (a `:description` on each parameter and field), `:authz`, a rule if the action is new, and tests: the Annex A table is in `authz-test`, and the table of operations with their statuses is in `docs-test`, which also fails for a missing description.

Tests: `apps/api/test-support` holds the harness (`pulse.api.test.harness`: fake identity provider, in-memory FHIR with the demo cohort, tokens for the demo people, `call`, a FHIR `spy`; `with-api` takes `:cors-origins`); `docs-test` and `security-test` check the document, Swagger UI, the headers and CORS through the whole handler; `stack-test` runs the api against the real stack with `bb test:it`, the sign-in of Swagger UI among it.

Gotchas learned the hard way: reitit-malli closes every `:map` schema and strips undeclared keys, so a FHIR resource in a response schema must be `[:map-of :keyword :any]` (a plain `:map` turned it into `{}`); malli does not apply defaults to `:optional` keys, so a parameter with a default is declared required with `:default` on its value schema; Reitit adds an `OPTIONS` endpoint to every route unless `::ring/default-options-endpoint` is nil; query parameters are only parsed if `parameters-middleware` is in the chain; muuntaja is restricted to JSON. In a query string a `+` is a space, so an offset such as `+02:00` must be sent as `%2B02:00` (the tests use `enc`); a `:fn` schema carries the message of a 400 (`:error/message`), and the explanation of an `:and` lists every failing child (a `:min` next to the `:fn` gave two messages, so the length is left to the `:fn`); the `:test` alias has Kaocha's `:main-opts`, so a scratch script needs the `:dev` alias; Kaocha captures standard output (a `println` in a test shows only if the test fails); test.check's `gen/let` has no `:let`, and `gen/double*` clusters near zero (use `gen/choose` to spread numbers over a range); a property test on an endpoint that changes state must create a new resource for every sample, or most samples meet a final state and are 409s (tally the statuses a generator produces before trusting it); the shape of a body is judged before the status of the resource, so a body that is wrong is a 400 even when the status would have been a 409; clj-kondo wants `Duration/ZERO`, not `(Duration/ZERO)`.

The document and the headers: the artifact is `fi.metosin/reitit-openapi` (not `metosin/`), and `ring-swagger-ui` 5.32.11, which `reitit-swagger-ui` pulls, lacks `oauth2-redirect.js` (the api pins 5.33.0); `reitit.ring/router` sets its own `:coerce` (private), so the documentation is derived from the routes of the finished router; `reitit-openapi` overwrites `components.schemas` with the schemas it found, so the shared `Problem` is added after it; malli's `:json-schema` property replaces the generated JSON Schema (a `:fn` is otherwise `{}`), a `:multi` default branch becomes an overlapping `oneOf` alternative (word the error with `:error/message` on the `:multi` instead), and a parameter with a `:default` is required for the coercion and marked not required by `docs`; a response with no `:description` makes the document invalid. Swagger UI takes the OAuth client and PKCE only from `initOAuth` (our `swagger-initializer.js`, served by name), and its sign-in popup needs `window.opener`: never set `Cross-Origin-Opener-Policy` on `/docs`. Reitit's resource handler matches by prefix and ignores the method (`docs/ui-handler` guards both; ring refuses `..`), and ring serves `.js` as `text/javascript`. The policy of `/docs` was checked in headless Chrome over the DevTools protocol (a Node script with no dependencies, not in the repository: extra X-47): a control that must be blocked, such as an inline script, has to be seen by the check before "no violations" means anything.

## apps/scheduler

Under construction (Phase 5): the schedule, the executor, the HTTP surface, the rules engine, the device simulator and the reminders are done; the catalogue of jobs (`pulse.scheduler.jobs/catalogue`) holds `evaluate-rules`, `simulate-devices` and `send-reminders`, and what is left of the phase is the api's side of the status of the jobs (step 7). `pulse/scheduler/config.edn` is the Integrant system map, read and checked like the api's (profile `dev` or `test`, chosen with `SCHEDULER_PROFILE`; closed maps). `schedule` ([ADR-0019](docs/adr/0019-scheduler-jobs-as-data-and-a-pure-next-run.md)): a schedule is EDN, either `{:type :interval :every-ms n}` (optionally `:offset-ms`; the grid is counted from the epoch, so when the process started changes nothing) or `{:type :daily :at "HH:mm[:ss]" :zone "Europe/Madrid"}`; `schema`, `valid?` and `problems` are what the configuration will be checked with, and `next-run` is pure: the first instant strictly after the one given, with no clock and no state. `job` is `{:id :description :schedule :handler}` (the id is a simple lower-case keyword, because it will go in URLs) and `check!` validates a catalogue, ids unique.

`executor` ([ADR-0020](docs/adr/0020-scheduler-executor-and-http-surface.md)): the ticks fire on one daemon thread (`ScheduledThreadPoolExecutor`) and the handlers run on virtual threads named `job-N`. A tick first arms the next tick, for `next-run` asked from the later of now and its own moment, and then runs the job unless it is still running (that tick is skipped, counted and logged): so a job never overlaps itself, a pause or a long run is not made up for, and the chain of ticks outlives a handler that fails or hangs (handlers must be safe to repeat). The state is one atom with a map for each job, changed by `swap!`, so claiming a run is atomic. `status` and `job-status` are data; `run-now!` answers `:started`, `:already-running`, `:unknown-job` or `:stopped` and does not move the schedule; `stop!` ends the ticks, waits `:grace-ms` for the handlers and interrupts the rest. A handler takes `{:job-id :trigger :due :started-at}` and returns nil or a map of simple values; an interruption is an `InterruptedException` anywhere in the cause chain; the status shows the class of an error and never its message. The clock, the tick scheduler and the workers are parameters, which is how the tests drive time by hand: `pulse.scheduler.test.time` (in `apps/scheduler/test-support`) has `world`, `advance!`, `fire-next!`, `set-time!` and `direct-workers`, and real virtual threads with a promise as a gate are used where two things must happen at once.

The HTTP surface is a second resource server, built like the api's without CORS: `authz` (`rules` as data from action to roles, `:jobs/read` and `:jobs/run`, both `clinic-admin`; deny by default through `check-routes!`; `:pulse.audit/access` events of the shape the api's have), the verifier's audience `pulse-scheduler` (a token meant for the api is a 401 here, and the other way round), `routes` (`/healthz`, `/readyz`, `GET /jobs`, `POST /jobs/{id}/run` that answers 202, 404, 409 or 503; the views are camelCase with ISO strings), `handler` and `security`. `pulse.scheduler.test.harness` (`with-scheduler`, `token-for`, `call`) wires the handler to a fake identity provider and an executor in fake time. `GET /api/admin/jobs` in the api (step 7) will call it with the api's own service-account token. The scheduler's own token comes from `:pulse.scheduler/token` (client `pulse-scheduler`, the secret from `SCHEDULER_CLIENT_SECRET` as a `#secret`, `KEYCLOAK_TOKEN_URI` for the address inside a container); nothing is asked of Keycloak until a token is needed, and `/readyz` has a `token` check, so a wrong secret shows as unready and not as jobs that fail. The dev profile cannot load without the variable, so the tests read it with `*environment*` set. `/readyz` also asks the api (`GET /readyz`, with the scheduler's token) and FHIR; the status of a job shows the keys of its result in camelCase.

The rules engine ([ADR-0022](docs/adr/0022-rules-engine-rules-as-data-alerts-raised-once.md)): `rules` (`defrule` defines a var holding a rule's data and its condition twice, as the function that runs and as the quoted form of the same text, checked against a schema when the namespace loads; `evaluate` is a pure multimethod on `:recent-count`, `:window-count` and `:rise`, from a rule, readings and `now` to nil or `{:readings :newest-at}`; readings go in a total order, by time and then by their numbers, because a server does not order those of one instant; a rise is compared in rationals, since 64.1 − 62.1 is 1.999999999999993 in doubles; `query` says what to ask the source for, from a second before the look-back), `alerts` (the Flag of a rule, a patient and the newest reading that supports it, identified as `R1/pt-ana/2026-10-13T08:00:00Z`; `raise!` is `c/create-once!`, a conditional create in a one-entry transaction, so an alert that exists, active or acknowledged, is left as it is; `active?` finds the active alert of a rule and a patient by the prefix `R1/pt-ana/`, with its slash, so that `pt-ana-2` is not `pt-ana`), `source` (`DataSource`; `ApiSource` reads the patients and the series through the api with the scheduler's token and the active conditions from FHIR, because Annex A gives `rules-engine` neither the patient nor the summary; `reading-from-item` puts an item in the stored unit and drops one that cannot be used, so that one odd reading does not stop the others) and `engine` (`run!` goes patient by patient and returns a summary; `failure/fatal?` (shared with the reminders) says which failures end the run: an interruption, no token, the api or FHIR unreachable or failing, the api refusing the token; a patient that fails is counted and logged; an alert raised is a `:pulse.audit/write` event with the scheduler's client as the actor). `jobs/catalogue` builds `evaluate-rules` from the components when it is `:enabled?` (not in the tests); a run with failed patients throws, so that it shows as a failed run. Tests: `rules-test` (the macro and what it expands to, the examples of Annex C with their boundaries, properties), `alerts-test`, `source-test` against a stand-in for the api, `engine-test` (the cohort seeded at each hour of the day, against a source read from the cohort and FHIR in memory) and `end-to-end-test`, which serves the api's own handler with Jetty and runs the engine against it: the four alerts of Annex C, raised once, an acknowledgement kept, and a patient's token refused with a 403. The harness (`with-scheduler`) takes `:fhir` and has a stand-in for the api whose answer a test changes through `:api-answer`.

The device simulator ([ADR-0023](docs/adr/0023-device-simulator-core-async-pipeline-to-a-fhir-transaction.md)): `simulator` (`scenario` makes the devices out of the signals of the cohort and the settings in `resources/pulse/scheduler/simulation.edn`, and fails at the start when they are wrong; `plan` is a pure function of the scenario, the number of the tick and its instant: a device is due every second tick at its own turn, its reading is the baseline of the signal at that hour of the day with a noise that is drawn again if it is further than 2 standard deviations, so that a normal reading cannot cross a threshold of Annex C, and an *episode* of the settings takes over its signal for the ticks it lasts: one for each rule, in a cycle of 32 ticks; `observation` is what the api makes of a reading, `measurement/normalize` and `measurement/observation`, with no performer, a `device` and the tag `https://pulse.example/tag|simulated`, under an id made of the patient, the signal and the second; `tick!` sends a plan through the pipeline) and `pipeline` (generic: a producer thread puts a lazy sequence on a bounded channel, `pipeline` runs the transducers keeping the order, a `partition-all` transducer on a channel makes the batches and flushes the last, one writer thread, not a `go` block since it does blocking I/O, writes each; a batch that fails is counted and logged and the next go on; an interruption or a timeout closes the source, gives what is in the pipeline `:drain-ms` to be written, and throws an ex-info of type `::interrupted` or `::timeout` with the stats, the first with the `InterruptedException` as its cause, which is how the executor knows it). The job `simulate-devices` counts its ticks from the start of the scheduler, so the first episode begins with it, and fails if a reading could not be made or written. The tests apply the rules to 70,000 normal readings (none may satisfy a condition, and no weight may rise 2 kg), run each episode through its rule (it must fire on at least two ticks in a row, that is for 30 seconds, since the engine runs every 30), and `pulse.dev-test` is the acceptance of the phase: the real systems of the api and the scheduler in one JVM, the simulator's readings seen by the api, the alert raised and found in the inbox of the practitioner.

The appointment reminders ([ADR-0024](docs/adr/0024-appointment-reminders-a-communication-sent-once-from-what-fhir-holds.md)): `reminders` (`query` is the search for the booked appointments that begin after `now` and no later than the window after it, in whole seconds so that HAPI and the fake agree to the second; `reminder-key` is `<appointment id>/<start in UTC>`, so an appointment that moves gets a new reminder; `practitioner-name` is the given and family names with no title; `message` is the text, in English whatever the language of the machine and in the zone of the clinic, `Reminder: your appointment with Elena Rivera is on Wednesday 14 October at 06:00 (Hypertension follow-up).` (the formatter is made in each call so that a test can change the default locale and see that it makes no difference); `communication` is the completed reminder with the identifier and no id; `run!` makes one search of the clinic and a `c/create-once!` for each appointment, reads each doctor once for the run, and returns `{:appointments :sent :already-sent :failed}`; an appointment that fails is counted and logged, `failure/fatal?` ends the run, and a reminder sent is a `:pulse.audit/write` event with the action `:reminder/write` and the rule `R5`, never the text). `failure` holds `fatal?`, which the engine had as a private function; it now also says that an interruption ends a run, since a handler must not swallow one (ADR-0020). The job `send-reminders` (settings `:window-hours`, 1 to 168, and `:zone`; `SCHEDULER_REMINDERS` and `SCHEDULER_REMINDERS_EVERY_MS`) reads and writes FHIR and not the api, so it works with the api down, and fails if a reminder could not be sent. Tests: `reminders-test` (the edges of the window to the second, the text through the days the clocks change and with the language of the machine changed, one reminder for each appointment and time, a failure of one appointment and one of the infrastructure, the audit, the cohort hour by hour, and a property against an oracle), `failure-test`, `stack-test` (HAPI and the fake remind the same patients, and HAPI finds the reminders valid) and, in `pulse.dev-test`, the acceptance: in the full system the cohort's appointment of Ana is reminded once.

Gotchas learned the hard way: a property test that shuffles must generate the permutation (`gen/shuffle`), or a failure cannot be repeated or shrunk; the `:test` classpath (`clojure -Spath -A:test`, plus the test directories) run with `clojure.main` and `clojure.test/run-tests` takes about 18 seconds against 70 through Kaocha, and a loop of hundreds of runs in one JVM is how a failure of one run in sixty was found (two readings of one instant gave an answer that depended on their order) and what makes mutation analysis affordable: each mutated source is evaluated in that one JVM (`load-string` of the mutated text, nothing written to disk, so a killed run leaves no file mutated) and the test namespaces are reloaded after it, because they capture rules and protocols at load time (a `defprotocol` is made anew by the reload, so a `reify` of it must be too); a JVM for each of the 250 mutations of step 4 would have taken hours, and a file mutated on disk and then left by a killed run had to be put back by hand. The tests of step 4 were strengthened by what it found: boundaries of the windows and of the status codes that end a run, readings of one instant, the encoding of a name in a query, the form of a `Location`. `engine/run!` excludes `clojure.core/run!` in its `ns`. HAPI answers a conditional create with a 201 and the `Location` `Flag/123/_history/1`, or a 200 for the one that was there; the condition is a query string and goes encoded. A stub server that records requests must record the raw path, or an encoded segment looks like what it was meant to be. A system test that enables a job with its real schedule can have the job fire in the middle of it (a 15-second interval did, one run in ten): give the jobs a test runs by hand a schedule of a week, which the epoch grid makes fire on Thursdays at midnight UTC. A search of the in-memory client is lazy and each page is computed from the state at that moment, so deleting while walking it skips resources: realize it first (`doall`). In bash `((` starts an arithmetic expression, so a group of commands that begins with two parentheses is not one. A function of `pulse.fhir.client` is mutated as a copy of itself evaluated with `in-ns`, because evaluating the whole file makes the protocol `FhirClient` anew and leaves the clients that were loaded with the old one. `t/with-signals` returns a throw as its `:error` and does not throw it. `(.plus instant n unit)` with an `n` that comes from a `range` is reflection: `(long n)`. Gotchas of the schedule and the executor: a daily time that the clocks skip runs right after the gap, and one they repeat runs the first time (`ZonedDateTime/of` does both); `next-daily` tries the days from one before to two after the date of `after`, and both ends are real: Greenland's clocks go from 23:00 to 00:00 (since 2024), so the 23:30 of a day comes out at 00:30 on the next date, and Newfoundland's went back at 00:01 to 23:01 (until 2010), so the next day's 00:00 had already happened. Mutation checks found that a random zone and moment never reach either (a range of two days survived), so the tests build cases from every such change in the JDK's time zone database and count that they get there; the daily property tests compare with an oracle that walks the minutes (valid for times without seconds in zones with whole-minute offsets); a scratch script that needs the test directory runs with `clojure -Sdeps '{:paths ["apps/scheduler/test"] :deps {org.clojure/test.check {:mvn/version "1.1.3"}}}' -M:dev script.clj` (the `:test` alias would run Kaocha). A `reify` of an overloaded method (`schedule` of a `ScheduledExecutorService`) must name the return type on the method (`(^ScheduledFuture schedule ...)`), and one with a hinted parameter and a single match must name it too (leave the hints off `execute`). A `ScheduledThreadPoolExecutor` keeps an exception thrown by a task in its future and says nothing, so a tick catches everything and arms the next tick first. `with-redefs` on a private function works through its var (`executor/claim!`) and is how a failing tick is simulated. `bound-fn*` carries Telemere's log context to another thread, which is how a manual run's events keep the request id. The threshold of a generator-coverage test is set from the measured mean and spread, not a round number below it (100 against a mean of 122 failed one run in fifty). A test that waits for a job to be idle and then reads what its worker logged races: the state is set before the event is logged; look at what the worker saw from inside it (`t/*ctx*` in the handler). A deftype needs `equals` and `hashCode` for two readings of the same file to be equal configurations (`Secret`).

## Local stack

Everything binds to 127.0.0.1: Keycloak 8080 (management/health 9000), HAPI FHIR 8090 (`/fhir`, `/actuator/health`), PostgreSQL 5432. About 1.5 GB of RAM in total. Demo users and their password come from `tools/realm.clj` and `.env` (`DEMO_USER_PASSWORD`). HAPI has no container healthcheck (distroless JRE); `bb up` polls it from the host. HAPI caches searches for about a minute (send `Cache-Control: no-cache` when testing).

`docs/` is the source of truth:
- `docs/02-implementation-plan.md`: concept, architecture, phases with checklists and acceptance criteria. Read the current phase before starting work and tick items as they are completed.
- `docs/01-stack-review.md`: why each dependency was chosen, with versions as of 2026-10-13.
- `docs/03-extras-backlog.md`: everything deliberately deferred. Add new ideas there instead of expanding the current phase.

## What it is

Remote patient monitoring and appointment coordination on FHIR R4 with Keycloak SSO. Four apps of different kinds share one realm (`pulse`) and one FHIR server (HAPI): `api` (resource server and FHIR gateway), `web` (server-rendered patient portal), `spa` (ClojureScript clinical workspace) and `scheduler` (rules engine and simulator).

## Working agreements

- Everything written in the repository is in English: code, comments, UI text, docs, ADRs, commit messages. The conversation with the owner is in Spanish.
- Document first: a stack or architecture change gets a short ADR (`docs/adr/`, created in Phase 1) before the code.

## Workstation (Windows 10; PowerShell and Git Bash)

- The Clojure CLI is the `clj-msi` build (deps.clj, `clojure --version` prints "Clojure CLI version (deps.clj)") in `%LOCALAPPDATA%\Apps\clojure`. Babashka comes from winget. npm is 11.21 (npm 12 needs Node ≥ 24.15 and the machine has 24.12). `JAVA_HOME` is set at user level.
- Processes started before Phase 0 (VS Code, its terminals, agent shells) do not see the new `PATH`. If `clojure` or `bb` is not found, restart VS Code or prepend `%LOCALAPPDATA%\Apps\clojure` and the Babashka winget package folder to `PATH`.
- Docker Desktop is capped by `~/.wslconfig` at 6 GB and 6 CPUs. Free RAM is scarce (about 0.7 GB with Docker idle), so do not start the full stack casually.
- The project path contains a space (`Clojure Porfolio`): always quote paths.
- In PowerShell, `"text $var: more"` is parsed as a scope-qualified variable and fails; write `${var}:`.
- In Git Bash, prefix `docker exec`/`docker cp` that use container paths with `MSYS_NO_PATHCONV=1`, or `/tmp/x` becomes a Windows path.
- Double quotes inside an argument that Java hands to `bb.exe` (`clojure.java.shell/sh`) are lost on Windows: a test that runs `bb -e` writes the expression without them, such as `(env/get-var (name :SCHEDULER_CLIENT_SECRET))`.
- `babashka.http-client` has no cookie jar and Cheshire's pretty printer emits CRLF on Windows (see `tools/kc.clj` and `tools/realm.clj`).
